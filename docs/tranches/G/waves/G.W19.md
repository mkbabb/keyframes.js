## §State, verified (file:line)

- **The three fields the demo transplants are public-but-internal — they have no first-class "adopt" verb.** `Animation.options: AnimationOptions` (`engine.ts:89`), `compiler!: FrameCompiler<V>` (`engine.ts:98`), `unflatten: boolean = true` (`engine.ts:142`). The demo writes all three directly: `animation.options = compiled.options; animation.compiler = compiled.compiler; animation.unflatten = compiled.unflatten;` (`useKeyframeOps.ts:107-109`). This is the ONLY place in `demo/` that assigns into the engine's internals (MD-1).
- **The live-options-reference invariant the seam MUST preserve.** The compiler is constructed `new FrameCompiler<V>(this.options)` (`engine.ts:233`) and holds `private options` as a LIVE REFERENCE to the owning `Animation`'s `options` object — "the setters mutate it in place, never replace it, so the NEXT compile always reads the current `duration`/`easing`/`colorSpace` without re-linking" (`frame-compiler.ts:99-110`). The constructor wires the compiler BEFORE `setOptions` precisely so the setters mutate the SAME object the compiler reads (`engine.ts:229-233`).
- **The invariant is test-LOCKED (the `6e29236` regression).** `test/frame-compiler.test.ts` "reads the LIVE options object — post-construction mutations are seen": construct `fc = new FrameCompiler(opts)`, `parse` → `frames[0].time.stop === 1000`; then `opts.duration = 2000` (the SAME object the setters mutate) and re-`parse` → `frames[0].time.stop === 2000`. "A copy here would silently desync duration/colorSpace from the playback class — the split's subtlest failure mode" (`6e29236`, `test/frame-compiler.test.ts` the "reads the LIVE options object" + "carries no playback state" cases).
- **The demo's exact current hazard — the invariant is held by a COMMENT, not the seam.** `useKeyframeOps.ts:96-101` reasons in prose: "`compiled` is built with the same targets, and its compiler holds `compiled.options` — which we adopt — so the compiler's live options reference stays consistent (no stale re-parse)." The order of the three assignments is load-bearing and un-enforced: `compiled.compiler` holds (privately) a reference to `compiled.options`; transplanting `animation.compiler = compiled.compiler` WITHOUT also `animation.options = compiled.options` would leave `animation.options !== animation.compiler.options` — the setters would mutate `animation.options` while the compiler reads the other object, the EXACT desync `6e29236` locks against. The demo gets it right TODAY only by convention; a future edit reordering or dropping a line silently re-introduces the desync with no gate.
- **`_stableKeys` is recomputed only by `parse()` → `computeStableKeys()`.** `_stableKeys` is `private` (`engine.ts:174`), exposed read-only via `get flatKeys()` (`engine.ts:184-186`), recomputed by `computeStableKeys()` (`engine.ts:296-302`, called at the tail of `parse()` at `:286`). The demo's three-field transplant ADOPTS `compiled.compiler.frames` (the already-compiled frames) but does NOT recompute the LIVE animation's `_stableKeys` — so after the reach-in, `animation.flatKeys` reflects the PRE-edit key-set, not the adopted compiled frames'. (The demo happens to not re-read `flatKeys` between adopt and the next `parse`, so it has not bitten — but the seam must recompute to be correct: the buffer-sizing contract `flatKeys` carries (`engine.ts:165-172`) depends on it.)
- **The DI/pipeline posture the seam preserves (ALREADY-SOTA — do NOT touch).** The compiler is constructor-injected (`engine.ts:233`), the compile is a clean staged facade delegated through `addFrame`/`parse`/the frame accessors (`engine.ts:248-302`), zero non-idiomatic dynamism (MD-2/MD-3/MD-4). The seam is purely ADDITIVE — one method + a field→accessor tightening — and changes NONE of this.

## §Goal

Give the engine the first-class "adopt-compiled-state" verb the demo is forced to hand-roll across the boundary: a ~10-line additive `Animation.adoptCompiled(source: Animation<V>): this` that transplants the `{ options, compiler, unflatten }` triad as ONE atomic motion, re-binds the compiler's live-options reference (so `this.options === this.compiler.options` post-adopt — the `6e29236` invariant), and recomputes `_stableKeys` (so `this.flatKeys` reflects the adopted compiled frames). The demo callsite collapses from three internal-field writes to one verb: `animation.adoptCompiled(compiled)`. The `compiler` field then tightens to a `get`-only accessor — the only writer becomes `adoptCompiled` + the constructor, so the reach-in is no longer expressible. The invariant moves from a demo COMMENT into the ENGINE, enforced by a gate. KISS · DRY · zero new machinery — one method, no new class, no new state.

## §Scope

- **S1 — add `Animation.adoptCompiled(source): this` (MD-1).** A ~10-line public method on `Animation` (`engine.ts`, near the frame-compiler delegation block `:248-302`) that, given a `source: Animation<V>` whose `compiler` is already compiled:
  1. Adopt the compiler: `this.compiler = source.compiler` (the compiled `frames`/`templateFrames`/`parsedVars` come with it).
  2. Re-bind the live-options reference ATOMICALLY: `this.options = this.compiler.options` — read the options object OFF the adopted compiler (not off `source.options` independently), so `this.options === this.compiler.options` is true BY CONSTRUCTION, not by the caller's ordering discipline. (This is the line the demo's three-write form leaves to convention; here it is the method's invariant.)
  3. Carry the rest of the adopted state: `this.unflatten = source.unflatten`.
  4. Recompute the stable key-set: call the existing `computeStableKeys()` so `this.flatKeys` reflects the adopted compiled frames (the buffer-sizing contract `engine.ts:165-172`).
  5. `return this` (chainable, the engine's house style — `addFrame`/`parse` both `return this`).

  **WHY:** the demo's three-field reach-in encodes a compiler-internal invariant (the compiler's `private options` reference, `frame-compiler.ts:110`) in demo prose (`useKeyframeOps.ts:96-101`); the engine OWNS that invariant and is the only place that can enforce it at the seam. Reading `this.options` off the adopted compiler (S1.2) makes the desync `6e29236` locks against UN-EXPRESSIBLE through this verb (`a-modularity-deep` MD-1). Because the compiler's `options` is `private` (`frame-compiler.ts:110`), the method does NOT poke into the compiler — it transplants the compiler whole and re-derives `this.options` from `source.compiler.options` via the public path (see §Design decisions on the `options` read).

- **S2 — collapse the demo callsite (MD-1, demo half).** `useKeyframeOps.ts:107-109` (`animation.options = compiled.options; animation.compiler = compiled.compiler; animation.unflatten = compiled.unflatten;`) collapses to `animation.adoptCompiled(compiled);`. The load-bearing prose comment (`:96-101`) shrinks to a one-line reference to the verb ("SINGLE COMPILE (E.W8 S0): adopt the throwaway's compiled state — `adoptCompiled` re-binds the live-options reference and recomputes the key-set"). **WHY:** the demo no longer reaches across the boundary — the invariant it described is now the engine's, gated; the comment no longer has to carry an un-enforced contract (Mandate: every contract that bears weight is enforced where it lives, not narrated at a distance).

- **S3 — tighten `compiler` to a `get`-only accessor (the natural tail, same proof).** With `adoptCompiled` the only consumer-facing writer of `compiler`, change `compiler!: FrameCompiler<V>` (`engine.ts:98`) to a backing `private _compiler!: FrameCompiler<V>` + a `get compiler(): FrameCompiler<V>` accessor (read-only). The two INTERNAL writers re-target the backing field: the constructor (`engine.ts:233` → `this._compiler = …`) and `adoptCompiled` (S1.1 → `this._compiler = source.compiler`). All read sites (the delegation getters `engine.ts:254-269`, the setters' `this.compiler.renormalizeColors()` at `:499,517`, `parse`'s `this.compiler.parse(...)` at `:285`) are unaffected — they read through the accessor. **WHY:** once the verb exists, an external `animation.compiler = …` write is the very reach-in we closed; making `compiler` read-only makes the reach-in a COMPILE error, not a convention (fail-explicit, Mandate). This is the natural tail — gated on the SAME `proof:adopt-compiled` (the accessor must still satisfy `a.compiler === b.compiler` post-adopt). (`options` and `unflatten` stay writable: the setters mutate `options` in place by design, and `unflatten` is a plain public toggle — only `compiler` was ever the reach-in vector that a writer could desync.)

## §Hard gate (falsifiable · re-runnable · MUST bite)

A new `proof:adopt-compiled` — a value-assertion test (`test/adopt-compiled.test.ts`) + a `scripts/proof-adopt-compiled.mjs` runner (the F advisory→hard idiom), wired into `npm test` and the `proof:*` set — with THREE clauses, each with a STATED bite. Build two compiled animations `a` and `b` (each `new CSSKeyframesAnimation(...).fromKeyframes(...)` over the same targets, `b` with a DIFFERENT key-set than `a` — e.g. `a` animates `opacity`, `b` animates `opacity` + `translateX` — so the `flatKeys` clause is non-vacuous), then `a.adoptCompiled(b)`:

- **`proof:adopt-compiled` (a) — the compiler is adopted.** Assert `a.compiler === b.compiler` (reference identity — the adopted compiler IS `b`'s, the compiled `frames` come with it). **BITE:** an `adoptCompiled` that re-compiles instead of transplanting (a fresh `FrameCompiler`) → `a.compiler !== b.compiler`, reds. Re-runnable: `npm run proof:adopt-compiled`.
- **`proof:adopt-compiled` (b) — the live-options reference is RE-BOUND (the `6e29236` invariant).** Assert `a.options === a.compiler.options` (the live-options reference held — the SAME object the setters mutate is the one the compiler reads), AND, the dynamic witness: `a.setDuration(2000); a.parse(); a.frames[0].time.stop === 2000` (the post-adopt setter mutation flows to the adopted compiler's next compile — the `6e29236` lock, re-asserted through the seam). **BITE (the demo's exact current hazard):** transplant `compiler` WITHOUT re-binding `options` (set `a.compiler = b.compiler` but leave `a.options` pointing at its old object — the three-write form with the `options` line dropped/reordered) → `a.options !== a.compiler.options`, AND the dynamic witness reds (the setter mutates `a.options`, the compiler reads the stale object, `time.stop` stays `1000`). This is the falsifiable proof the seam closes the desync the demo held by convention.
- **`proof:adopt-compiled` (c) — `_stableKeys` is recomputed.** Assert `a.flatKeys` reflects `b`'s compiled key-set (e.g. `a.flatKeys` now contains `translateX`, `b`'s extra key, and equals the union of `b`'s compiled-frame `flatVars` keys — NOT `a`'s pre-adopt key-set). **BITE:** an `adoptCompiled` that adopts the compiler but skips `computeStableKeys()` → `a.flatKeys` stays the pre-adopt set (missing `translateX`), reds (the buffer-sizing contract `engine.ts:165-172` would be stale).

**The §Mandate bar — MUST bite.** Clause (b)'s BITE is the demo's literal current hazard transplanted into a test: `compiler` without `options` re-bind → reds on both the identity AND the dynamic-mutation witness. No clause passes vacuously: (a) is reference identity, (b) re-asserts the `6e29236` dynamic lock THROUGH the new verb, (c) requires a DIFFERENT key-set on `b` so a no-op `computeStableKeys` is caught. With S3, an external `a.compiler = …` write is additionally a COMPILE error (the read-only accessor) — a second, stricter bite at the type level.

## §Design decisions (trade-offs RESOLVED)

- **An additive VERB, not a setter or a copy — RESOLVED.** Three shapes were on the table: (i) leave the three-field reach-in (status quo — the invariant stays a demo comment, un-gated); (ii) a `set compiler(c)` setter that re-binds `options` on assignment; (iii) the `adoptCompiled(source)` verb. (iii) wins: the operation is INTRINSICALLY a triad transplant (`{ options, compiler, unflatten }` move together — a single `set compiler` could re-bind `options` but not carry `unflatten`, and would still let the caller think in three writes); a verb names the whole atomic motion ONCE and recomputes `_stableKeys` as part of it. A deep COPY (re-compile) is rejected — it would discard the `6e29236` single-compile property (the throwaway's `fromKeyframes` is the ONE compile, E.W8 S0, `useKeyframeOps.ts:96-105`); `adoptCompiled` TRANSPLANTS the already-compiled state, preserving single-compile (`a-modularity-deep` MD-1).
- **`this.options = this.compiler.options`, read off the ADOPTED compiler — RESOLVED.** The re-bind reads `options` from the just-adopted compiler, NOT independently from `source.options`. Both reference the same object today, but reading off the compiler makes `this.options === this.compiler.options` true BY CONSTRUCTION — the method cannot produce a desynced state even if a future `Animation` ever held an `options` distinct from its compiler's. The compiler's `options` is `private` (`frame-compiler.ts:110`); to read it the natural path is to keep the invariant that `Animation.options` IS the compiler's options object (the constructor establishes it at `:227-233`), so `adoptCompiled` re-establishes the SAME identity by sourcing both from `source.compiler`. (If value.js ever needs the read without the identity assumption, a `FrameCompiler.options` get-accessor is the seam — RECORD-only, not needed here since the constructor already guarantees the identity.)
- **`get`-only `compiler` is the natural tail, same proof — RESOLVED.** S3 is not a separate wave: once `adoptCompiled` is the only consumer-facing writer, an external `animation.compiler = …` is the reach-in we closed — making the field read-only makes that reach-in a COMPILE error (fail-explicit), and the accessor must still satisfy `proof:adopt-compiled` (a) (`a.compiler === b.compiler`). The two internal writers (constructor `:233`, `adoptCompiled` S1.1) re-target a `private _compiler` backing field; all read sites are unaffected (they read through the accessor). `options`/`unflatten` stay writable — only `compiler` was the desync vector (`a-modularity-deep` MD-1).
- **In-place vs replace for `options` — RESOLVED (no in-place merge).** `adoptCompiled` REPLACES `this.options` with the adopted compiler's options object (re-binding the reference), it does NOT in-place-merge fields into the existing `this.options`. This is correct because the demo's intent is to ADOPT the freshly-parsed animation's options wholesale (the new CSS authored a new `duration`/`easing`/etc.); an in-place merge would keep stale fields from the pre-edit options. The replace is the single atomic re-bind the live-options invariant needs (`useKeyframeOps.ts:93-105`). (Contrast `updateAnimationFromKeyframeString` at `:122-151`, which `Object.assign`s into the LIVE options and re-`parse()`s — a DIFFERENT op (single-keyframe edit, no throwaway), not touched by G.W19.)
- **MD-6 (thin public JSDoc) — RECORD, optional rider — RESOLVED.** ~10 thin public methods (`onStart`/`onEnd`/`fillForwards`/…) lack JSDoc — a `proof:public-jsdoc` discipline-gate (assert every public method on `Animation` carries a JSDoc block), byte-cheap, foldable onto MD-1's engine touch IF G elects. RECOMMEND RECORD, not SHIP in G.W19: it is a hygiene sweep orthogonal to the seam correctness this wave proves, and bundling it would dilute the falsifiable `proof:adopt-compiled` bite with a stylistic gate. If G elects the JSDoc gate, it rides this wave's `engine.ts` touch (one PR, two proofs); otherwise it stays RECORD for a future hygiene pass (`_SYNTHESIS-perf-testing-engine.md §2:296-298`, `§4:381`). The `adoptCompiled` method itself, being a NEW public contract that bears weight (the live-options invariant), carries a full JSDoc block regardless — that is not the MD-6 sweep, it is the Mandate baseline for a new weight-bearing contract.
- **MED, not HIGH — RESOLVED.** The demo gets the invariant RIGHT today (the three writes are correctly ordered); this is a boundary-HYGIENE + future-proofing SHIP (enforce-at-the-seam vs narrate-by-comment), not a live correctness bug. Contrast `G.W17` (HIGH — a blend mode that DOES NOT RUN today). The MED rating reflects: real reach-in closed + a real desync hazard made un-expressible, but no current user-visible defect (`_SYNTHESIS-perf-testing-engine.md §1:110` "1 SHIP (MED)", `§THESIS:78`).
- **Independent of the spine, sequence-neutral — RESOLVED.** A kf-local additive engine method + a demo swap, ZERO dependency on the re-pin (`G.W2`) and disjoint files from `G.W17`/`G.W18` — orderable freely. It does not gate, and is not gated by, any other wave (`_SYNTHESIS-perf-testing-engine.md §2:299` "Independent of the spine").
