# Tranche-C Audit — Lane: Frontend-Design / Motion + Engine Dogfooding

The demo is keyframes.js's shop-window, yet it imports its own physics/interpolation engines in exactly **one** of seven motion surfaces — and even that one hand-rolls the rAF lifecycle the engine ships (`RAFPlayback.drive`). Reduced-motion (`prefersReducedMotion`/`withReducedMotion`/`respectReducedMotion`) — built into every engine play-path — has **zero references anywhere in the demo** (JS or CSS): the π probe B skipped is still open. Below, exhaustive within lane.

---

1. **[critical] Reduced-motion is wired through the whole engine but honored nowhere in the shop-window** — The engine ships `prefersReducedMotion()` + the one `withReducedMotion` gate (`src/animation/internal/reduced-motion.ts`), `RAFPlayback.play({respectReducedMotion})` (`playback.ts:91-134`), and `AnimationOptions.respectReducedMotion` (`constants.ts:116,143,158`). Demo proof of absence: `grep -rn "respectReducedMotion:" demo/` → **0 hits**; `grep -rn "prefers-reduced-motion" demo/` → **0 hits** (no JS, no CSS guard). `defaultAnimationOptions` (`demo/@/components/custom/animation-controls/stores/animationOptionsStore.ts:33-40`) omits the flag, so it defaults `false` for every scene; the always-on cube `idle-bob` (`CubeTarget.vue:133-146`) and the `infinite alternate` amiga rotations (`amiga/useAmigaAnimations.ts`) run unconditionally for a user who asked the OS to stop motion. **Disposition: BOOK (must-ship for C).** **GESTALT fix:** set `respectReducedMotion: true` in `defaultAnimationOptions` so every engine-driven scene inherits the snap-to-rest path for free; gate the two hand-rolled motions that bypass the engine — wrap `idle-bob`/`rainbow` in `@media (prefers-reduced-motion: no-preference)` (the CSS twin of the engine gate), and short-circuit the spring/easing demo loops by consulting the engine's exported `prefersReducedMotion()` (dogfood the same authority the heavy path uses) to snap each tracker to its target instead of animating. One detector, fanned out — exactly the constellation posture the gate's doc-comment promises.

2. **[high] `AnimationVisualizer` re-implements `SmoothProgress` + a spring-decay coast by hand** — `AnimationVisualizer.vue:114-169` hand-rolls (a) exponential velocity smoothing `velocity = velocity*0.6 + instantV*0.4` (line 121) and (b) a friction-decay coast loop `velocity *= FRICTION; coastProgress += velocity*dt` with its own `requestAnimationFrame(coast)` (lines 150-168). These are textbook `SmoothProgress` (exponential smoothing) and `SpringProgress` (analytic decay-to-rest) — the engine's two flagship light trackers — yet the showcase's own scrubber ignores both. **Disposition: BOOK.** **GESTALT fix:** replace the velocity estimator with `SmoothProgress` and the release coast with a `SpringProgress` seated to the boundary, driven by `RAFPlayback.drive(spring, () => setBallProgress(spring.value))` — the `Tickable` contract (`playback.ts:30-35,142-159`) auto-stops on `settled` and re-arms idempotently on re-seat, deleting `stopCoast`/`VELOCITY_EPSILON`/`coastRafId` bookkeeping. This is the single most legible dogfooding win: the primary control surface becomes a live `SpringProgress` advertisement and the inertia gets the analytic solver's correctness for free.

3. **[high] The spring showcase ships `SpringProgress`/`NumericAnimation` but hand-rolls the loop `RAFPlayback.drive` exists for** — `demo/spring/useSpringDemo.ts` is the ONE scene that instantiates light engines (`SpringProgress` ×3, `NumericAnimation` ×1), yet it still owns a raw `let rafId; requestAnimationFrame(tick)` (lines 117-160) calling `spring.tick(dt)` manually. `grep "RAFPlayback|.drive(" demo/spring/useSpringDemo.ts` → **0 hits**. The engine built `Tickable`/`drive` precisely for `SpringProgress`/`SmoothProgress` (`playback.ts:25-35,136-159` + `CLAUDE.md`), and `SpringProgress` already implements `Tickable`. **Disposition: BOOK.** **GESTALT fix:** the comparison row genuinely needs ONE shared clock to stay phase-aligned (the comment at line 45 is right), so this is the case for `RAFPlayback.loop(cb)` — own a single `RAFPlayback`, `loop` it, and step each tracker inside; or expose a tiny `RAFPlayback.driveMany(tickables[])`. Either way the demo stops re-deriving `dtMs = lastT ? now-lastT : 16.667` (line 128) which is byte-identical to `drive`'s own dt seed (`playback.ts:147`). **This is the ≥2nd-consumer pressure the engine surfaces need to avoid overfitting** — `drive` currently has only internal callers; the spring scene + finding #2 give it two independent external consumers, validating the contract shape.

4. **[high] The easing demo hand-rolls a ping-pong rAF that is `NumericAnimation` (alternate) verbatim** — `demo/easing/useEasingDemo.ts:120-194` computes `const phase = cycle % 2; progress = phase <= 1 ? phase : 2 - phase` over a manual `requestAnimationFrame(tick)` — this is exactly `direction: "alternate"` interpolation, which `NumericAnimation` provides. The scene already holds `currentEasingFn` as a callable `TimingFunction` (line 65), so it could feed a `NumericAnimation([{p:0},{p:1}], {timingFunction: currentEasingFn, ...})` directly — instead it hand-syncs `progress` and a separate `dummyAnimation` (lines 264-305) just to satisfy the bottom-bar scene contract. **Disposition: BOOK.** **GESTALT fix:** drive the preview with a real `NumericAnimation` whose `timingFunction` re-seats from `currentEasingFn` on change (no `dummyAnimation` shim, no manual ping-pong math), played via `RAFPlayback`. The easing scene demonstrating named curves should itself be powered by the engine that resolves them — and `resolveEasing(name)` (`easing.ts:68`) is the boundary-correct way to turn the string selector into the typed `Easing` the light path wants, instead of reaching into value.js `timingFunctions` directly (lines 1-9, 77).

5. **[medium] Amiga's Three.js render loop is a justified raw rAF — but the engine drives logic, not the renderer; keep the seam** — `AmigaScene.vue:99-122` owns `requestAnimationFrame(animate)` for `controls.update()` + `renderer.render()`. This is legitimately NOT a keyframes.js concern (it's the WebGL present loop), and the actual animation IS engine-driven (`AnimationGroup` in `useAmigaAnimations`). **Disposition: SHIP (no change) — RECORD the rationale.** **GESTALT note:** do NOT force the engine here; the correct dogfooding is that the `AnimationGroup` ticks the sphere transform (it does). The only refinement: the render loop runs unconditionally even when the group is paused/reduced-motion — couple `startRenderLoop` to render-on-demand when the group is settled to save battery. Record this boundary so C doesn't mis-file it as a hand-rolled-rAF debt.

6. **[medium] `SmoothProgress`, `ElementMorph`, `Timeline`/`ScrollTimeline`/`ManualTimeline`, `RAFPlayback` have ZERO demo consumers** — `grep -rEn "new (SmoothProgress|ElementMorph|Timeline|ScrollTimeline|ManualTimeline|RAFPlayback)" demo/` → **0 hits**. Five of the engine's eight light surfaces (`index.ts:30-48`) are unexhibited; a consumer browsing the shop-window cannot see them work. `ScrollTimeline` in particular ships injectable `getScrollY`/`getViewportHeight` (per root CLAUDE.md) and is invisible. **Disposition: BOOK (showcase gap).** **GESTALT fix (where to dogfood MORE):** (a) `ElementMorph` — the scene-switcher (`App.vue` `<component :is>` KeepAlive swap, lines 84-96) currently has no shared-element motion; morph the dock-pill/target rect between scenes — a `MorphRect`→`MorphRect` interpolation is the canonical `ElementMorph` demo AND gives the ≥2nd consumer `morph.ts` needs. (b) `ScrollTimeline` — bind a scene's hero animation `progress` to scroll via `ScrollTimeline` (its injectable callbacks make it the showcase-friendly surface). (c) `SmoothProgress` — finding #2 supplies its first real consumer. Each placement doubles as the overfitting guard: every light surface earns an independent external caller.

7. **[low] `useRafLoop` is a demo-local rAF primitive that duplicates `RAFPlayback.loop`'s self-rescheduling + guard semantics** — `demo/@/components/custom/animation-controls/composables/useRafLoop.ts` re-implements a guarded self-rescheduling loop (`loop`→`requestAnimationFrame(loop)` with a post-callback guard re-check, lines 19-29) that mirrors `RAFPlayback.loop(cb)`'s "callback returns continue" contract (`playback.ts:168-187`), minus the generation-counter restart-safety the engine added (`_gen`, lines 73,170-183). The demo's version can double-schedule on rapid start/stop — the exact bug `RAFPlayback._gen` was introduced to fix. **Disposition: BOOK.** **GESTALT fix:** rebase `useRafLoop` onto `RAFPlayback.loop` (wrap it in the Vue lifecycle adapter: `onUnmounted(() => playback.stop())`), inheriting the generation-safety and collapsing two rAF lifecycle implementations into one. The Vue composable becomes a thin reactive skin over the engine driver — dogfooding the restart-correctness the library already paid for.

8. **[low] `useTransformState` + `useTimeline` use bare `requestAnimationFrame` for one-shot debounce/settle — borderline, mostly fine** — `useTransformState.ts:205` (`requestAnimationFrame(() => updateTransformations())` as a write-coalescing debounce) and `useTimeline.ts:206` (`requestAnimationFrame(() => resolve())` to await one paint before snapshot) are single-frame schedulers, not animation loops — not engine work. **Disposition: SHIP (RECORD).** These are correct uses of raw rAF as a microtask-after-paint primitive; the engine has no surface for "run once next frame" and shouldn't grow one. Note for C: the matrix-editor's *actual* animations (`updateMatrixCell`/`animateUpdateMatrix`, lines 70-119) already dogfood `CSSKeyframesAnimation().fromVars().play()` correctly — good citizen, leave alone.
