1. **[INFO — the load-bearing WAAPI question, RESOLVED as correct] The css-twin gate does NOT cause a perf regression — it fixes a silent *correctness* bug, and the default-eased fall-to-rAF is the only faithful disposition.** `defaultOptions.timingFunction = { fn: easeInOutCubic }` with no `.css` (`constants.ts:156`); `cssTwinFor` returns `undefined` for all value.js bespoke names (`easing.ts:43-48`); so `isWAAPIEligible` rejects any default-eased multi-frame animation at `waapi.ts:97-102` (tested, `waapi-lifecycle.test.ts:83`). The lane's hypothesis — "ALL default-eased animations now fall to rAF, a perf regression hiding as correctness" — is **half-true on the mechanism but wrong on the verdict.** Pre-B (commit `6487c7f`) had no css-twin gate: `toWAAPIOptions` emitted `getCSSEasing(uniformTiming) ?? "linear"` (`6487c7f:waapi.ts:176`), so a default-eased animation that reached WAAPI would have run **bare `linear` on the compositor** — a silently *wrong curve*. Crucially, pre-B the WAAPI path was *dead in practice anyway*: the renderer was tagged with a `Symbol.for("keyframes.defaultRenderer")` (`6487c7f:renderer.ts:18-30`) that `Function.prototype.bind` dropped, so every `fromString` animation read as "custom transform" → ineligible. B's `usesDefaultRenderer` reference check (`engine.ts:197-203`, `resolveTransform` at `1141-1146` wires `_defaultTransform` into every `from*` frame) genuinely *resurrected* the path — and the css-twin gate is what keeps the resurrection faithful. So the true delta is: **dead-and-wrong-when-alive → alive-and-faithful (compositor only for curves that round-trip to CSS: explicit `cubic-bezier()`/`steps()`/CSS-keyword, and single-segment springs via their `linear()` twin).** **Disposition: SHIP.** No regression — a curve that cannot be expressed in CSS *must not* run on the compositor. **GESTALT (book for C, not a fix):** the residual is that the *default* curve has no compositor path at all. If C wants default-eased animations on the compositor, the gestalt is to make the **default easing itself css-twinnable** — ship the default as a `cubic-bezier()` literal (`easeInOutCubic ≈ cubic-bezier(0.645,0.045,0.355,1)`) carrying its own `.css`, so `defaultOptions.timingFunction = { fn: easeInOutCubic, css: "cubic-bezier(...)" }`. That single constant change moves the *entire default surface* back onto the compositor faithfully, with zero gate changes. This is the real perf lever the audit is circling.

2. **[MED — lifecycle gap the 16-finding review missed] `RAFPlayback.drive()` has no generation guard — the exact double-schedule class `loop()` was hardened against.** The review fixed `loop()` with a `_gen` counter so a `stop()`+restart mid-async-frame cannot re-arm a second rAF chain (`playback.ts:73, 168-187`, called out in commit `7fc60e5`). But `drive()` (`playback.ts:142-159`) uses only the `if (this._rafId !== null) return` idempotency guard and never touches `_gen`. `drive`'s `frame` callback is *synchronous* (no `await`), so the in-flight-async-frame race that bit `loop` cannot occur identically — **but** the asymmetry is a latent trap: `drive`'s guard is `_rafId !== null`, and `stop()` bumps `_gen` + nulls `_rafId`, so a `frame` that has *already captured* its closure and is executing when `stop()`+`drive()` interleave (possible if a `tickDt` or `onFrame` callback re-enters `setTarget`→`_startLoop`→`drive` synchronously) will see `_rafId` freshly repopulated by the restart and schedule on top of it. Spring/smooth `_onFrame` callbacks are consumer-supplied and *can* re-enter. **Disposition: BOOK.** **GESTALT fix:** give `drive` the same `_gen`-captured reschedule check `loop` has (`const gen = ++this._gen; … if (gen !== this._gen) return;`), or — cleaner — fold `drive` and `loop` into one generation-guarded primitive since both are "schedule frame, conditionally reschedule." The three-method split (`play`/`drive`/`loop`) is itself slightly over-shaped; `play` is `loop` + a clock + the reduced-motion gate, `drive` is `loop` + a settle-check. One guarded core with three thin entry shapes would delete the divergence that let `drive` miss the guard.

3. **[MED — naming incoherence the `Tickable` unification hid] `tick` / `tickDt` / `tick(dt)` mean four different things across the light steppers; the `Tickable` interface unifies only `tickDt`.** `SmoothProgress.tick(): number` takes no arg (frame-rate-*dependent*, fixed damping, `smooth.ts:106`); `SmoothProgress.tickDt(dt): number` takes **ms** (`smooth.ts:128`); `SpringProgress.tick(dt): number` takes **seconds** (`spring.ts:204`); `SpringProgress.tickDt(dt): number` takes **ms** (`spring.ts:221`, a units adapter over `tick`); `Timeline.tick()` takes none (`timeline.ts:129`). So `obj.tick(16)` means "advance 16 seconds" on a spring but "advance one damping step, arg ignored" on a smoother — a foot-gun for a consumer treating them polymorphically. The `Tickable` interface (`playback.ts:30-35`) only standardizes `tickDt(dt): void` + `settled`, which is correct for the driver but leaves the public `tick` surface incoherent. Also `Tickable.tickDt` is typed `: void` while both implementors return `number` (`smooth.ts:128`, `spring.ts:221`) — harmless (covariant) but signals the interface was retrofitted, not designed-through. **Disposition: BOOK.** **GESTALT fix:** make `tickDt(dt: number)` (ms) the *single* canonical step on every stepper and the only public one; demote `SmoothProgress.tick()` (the frame-dependent no-arg variant) and `SpringProgress.tick(dt-in-seconds)` to private/internal or delete them in favor of `tickDt`. `springLinearStops.ts:64` and `springTimingFunction.ts:88` call `spring.tick(dt)` in seconds internally — those become `tickDt(dt*1000)` or a private `_stepSeconds`. One step method, one unit, across all four — the unification the `Tickable` interface implied but didn't finish.

4. **[MED — fail-explicit contract half-honored] `setColorSpace` and `setHueMethod` silently bypass the `parseOption` seam they belong to.** The fail-explicit invariant (`errors.ts`, all nine other setters at `engine.ts:488-655`) is "present-but-malformed throws `AnimationOptionError`; only genuine `undefined` defaults." But `setColorSpace` (`engine.ts:657-662`) does `colorSpace ?? defaultOptions.colorSpace` — a malformed *present* value (e.g. `setColorSpace("srgbbb")`) is accepted and written, no throw. `setHueMethod` (`engine.ts:664-669`) writes any non-`undefined` value unchecked. The code comments rationalize this as "type-enforced at the boundary (value.js's ColorSpace union)" — but the setters take `InputAnimationOptions["colorSpace"]` and are reachable from `setOptions(rawObject)` / the demo's runtime-string controls where the TS union is *not* enforced. This is precisely the "silent permanent degradation" class the seam was built to kill, left unclosed on the two color setters. **Disposition: BOOK.** **GESTALT fix:** route both through `parseOption("colorSpace", raw, (r) => COLOR_SPACES.includes(r) ? r : undefined, ...)` against the value.js `ColorSpace`/`HueInterpolationMethod` enumerations — the same one-line pattern `setDirection`/`setFillMode` already use (`engine.ts:585, 611`). Closes the seam fully; no new surface.

5. **[LOW — structural duplication / contract smell in the one place it survived] `Timeline._advance` duplicates the `smoother.setTarget` call and splits the smoother-drive logic awkwardly across `_advance` + `finalizeProgress`.** `applyPipeline()` is documented "does NOT advance the smoother" (`timeline.ts:76-93`), then `_advance` (`timeline.ts:115-126`) calls `setTarget(raw)` + `tick()/tickDt()` in the interior branch, while the boundary branch defers to `finalizeProgress` (`timeline.ts:99-108`) which *also* calls `setTarget(raw)` + conditionally `snap()`. So `setTarget` is written in two places with subtly different follow-ups, and the boundary-snap logic lives in `finalizeProgress` while the interior-advance lives in `_advance`. It works (tested), but it's the one spot where the "one pipeline" intent didn't fully converge — a reader cannot see the whole sample→ease→snap→smooth flow in one function. **Disposition: BOOK.** **GESTALT fix:** collapse to a single `_advance(dt?)`: `const raw = applyPipeline(); smoother?.setTarget(raw); if (raw<=0||raw>=1) smoother?.snap(); else dt===undefined ? smoother?.tick() : smoother?.tickDt(dt); this.currentProgress = smoother?.current ?? raw;`. Deletes `finalizeProgress` (its only other caller is internal) and the duplicated `setTarget`.

6. **[LOW — `_snapSettled` asymmetry between the two sibling steppers] `SpringProgress._snapSettled` calls `_playback.stop()`; `SmoothProgress._snapSettled` does not.** `spring.ts:188-197` ends its snap with `this._playback.stop()`; `smooth.ts:99-103` is identical *minus* that stop. An inconsistency in the "one withReducedMotion contract drives all surfaces" claim: the *snap closures* are not behaviorally uniform. **Disposition: BOOK.** **GESTALT fix:** lift the `_playback.stop()` into a shared `snapSettled(emit)` helper (the W2 spec's S2 named exactly this — "a `snapSettled(target, emit)` helper") so both steppers' snap is one body, not two near-copies that already drifted by one line.
