# Frontend-Design Audit — Tranche B (keyframes.js demo) — LAYOUT · SPACING · RHYTHM · MOTION-CONTINUITY

**Summary:** B.W3 fixed the four-blank-scene blocker and the cube clip, but it paid for it by *deleting the scene-swap `<Transition>` and leaving its CSS orphaned* — scenes now hard-cut; on top of that the audit surfaced three genuinely-dangling layout tokens (`--dock-menubar-reserve`, `--spring-snappy`, `--dock-icon-height` in the shipped dist) that silently break the mobile controls-pane height clamp and the desktop pane slide, plus an unreconciled hero-over-cube collision on home-mobile.

### 1. **[high] The scene-swap `<Transition>` is gone and its CSS is fully orphaned — scenes hard-cut**
Evidence: `demo/app/App.vue:407-424` defines `.scene-enter-active / .scene-leave-active / .scene-enter-from / .scene-leave-to`, but a repo-wide grep finds **no `<Transition name="scene">` anywhere** in `demo/` (confirmed: `grep -rn 'name="scene"'` empty). The `<Suspense :key="activeSceneKey">` at App.vue:118 swaps the live component with zero transition. W3 commit `46eea7c` removed both `<Transition mode="out-in">` and `<KeepAlive>` because wrapping a keyed `<Suspense>` whose child is a `defineAsyncComponent` *never triggered the async loader* (App.vue:103-117 documents this empirically). So the dead CSS is a tombstone, and every scene change is a jarring hard-cut.
Disposition: **BOOK**.
GESTALT fix — *dogfood the engine* (the inventory's exact mandate, and the elegant transposition): do NOT restore a CSS `<Transition>` around `<Suspense>` (that re-breaks async loading). Instead drive an opacity/scale fade with the engine's own `SpringProgress` from `src/animation/spring.ts`, which already has the contract for this:
- On `activeSceneKey` change, run `spring.play((v) => sceneOpacity.value = v)` with `target` 0→1, binding `style="opacity: v; transform: scale(lerp(0.97,1,v))"` on the `<Suspense>`'s wrapper `<div>` (App.vue:118 host). The async loader stays on the bare `<Suspense>` — untouched — because the spring drives a *sibling style binding*, not a Vue `<Transition>` wrapper. No re-break.
- Construct it with `respectReducedMotion: true` (spring.ts:45,170-185): under `prefers-reduced-motion` the spring's `_snapSettled()` jumps to terminal in one emit, giving a clean instant swap with zero extra code. This is the engine's *own* reduced-motion authority (`internal/reduced-motion.ts`) animating its own shop-window — the dogfooding the brief asks for. Use the canonical `smooth` preset (`response: 0.5, dampingFraction: 0.86`, spring.ts:54-62) for a calm, no-overshoot enter; the leave can simply be the new scene fading *in* over the old (cross-dissolve via two stacked layers) so there's never a blank gap. Then delete App.vue:407-424.

### 2. **[high] `--dock-menubar-reserve` is undefined — the mobile controls-pane height clamp is invalid, so the open pane runs under the bottom dock (the "square/mobile box under the dock" cramping)**
Evidence: `AnimationControlsGroup.vue:461` sets the mobile controls-pane-wrapper `max-height: calc(100dvh - var(--dock-margin) - var(--dock-icon-height) - var(--dock-menubar-reserve))`. `--dock-menubar-reserve` is defined **nowhere** — not in `demo/@/styles/*.css`, not in glass-ui (verified: dangling against the built dist and source). A `var()` with no fallback inside `calc()` makes the **whole `calc()` invalid** → `max-height` falls back to the cascaded `100dvh` / `none` (line 451/486). The pane therefore claims full viewport height and its bottom content slides under the `AnimationMenuBar` (`AnimationMenuBar.vue:7`, `bottom: var(--work-area-bottom-offset)`, `z-dock`). This is the controls-open mobile cramp.
Disposition: **BOOK**.
GESTALT fix — name the missing token once, structurally. Add to `demo/@/styles/style.css` `:root` (where the other layout tokens live, style.css:18-26):
`--dock-menubar-reserve: calc(var(--work-area-bottom-offset, 0px) + var(--dock-icon-height) + var(--dock-margin) + env(safe-area-inset-bottom, 0px));`
This makes the bottom exclusion zone derive from the *same* dock primitives as the top offset (symmetry with `--work-area-top-offset`, style.css:25), so the open pane is clamped to the true content band and can never tuck under the menubar. This is also the structural home for W3 S5's "dock exclusion zones" finding — reserve top+bottom from one token pair rather than per-page.

### 3. **[medium] `--spring-snappy` is undefined — the desktop controls-pane slide-in falls back to instant/no-easing, breaking motion continuity**
Evidence: `AnimationControlsGroup.vue:509`: `transform var(--duration-slow) var(--spring-snappy)` on `.controls-pane--open .controls-pane`. `--spring-snappy` (and `--spring-smooth`, `--spring-bouncy`) resolve to **nothing** (verified dangling in both demo source and glass-ui dist). An undefined `transition-timing-function` value makes that transition declaration invalid → the springy "spring in from left" the comment promises (line 503-510) degrades to the browser default `ease` or no transition, so the 400px controls pane pops rather than springs. The intended "rotate(-2deg)" exit (line 513) likewise lacks its springy counterpart on entry.
Disposition: **BOOK**.
GESTALT fix — the engine already manufactures this exact curve as a CSS `linear()`. `src/animation/springTimingFunction.ts` emits a spring as a typed `Easing` whose `.css` is the faithful `linear()` twin, and `springLinearStops.ts` produces the stop string. Generate `--spring-snappy` from `SpringProgress({response:0.35, dampingFraction:0.65})` (the demo's own "Snappy" preset, visible in spring-mobile.png) via `springLinearStops`, emit it as `--spring-snappy: linear(...)` into `style.css`, and use it. Same dogfooding as finding 1 — the demo's spring CSS is *generated by the engine it demonstrates*, not hand-tuned cubic-beziers. (If a quick token is wanted as an interim: `--spring-snappy: var(--ease-spring)` reuses glass-ui's existing `cubic-bezier(.22,1.6,.36,1)` overshoot curve, which *does* resolve.)

### 4. **[high] Home-mobile: the hero text band and the centered cube occupy the same vertical zone → the start-screen prints over the cube faces**
Evidence: home-mobile.png shows "from the list ≣ above." and "or drag M. cubert" printed directly across the cube's yellow/red faces. `EditorStartScreen.vue:2` is `absolute left-0 top-0 z-content mt-28 h-0 w-screen` — pinned to the top, vertically centered hero. The cube (`CubeScene.vue` → `CubeTarget.vue:2`, `grid h-full items-center justify-center`) centers in the *stage row*, which on mobile is grid row 2 (`AnimationControlsGroup.vue:148`, `col-span-full row-start-2`) — the same vertical center of the viewport. The hero overlay (`EditorShell.vue:27`, `absolute inset-0 z-content … pointer-events-none`) sits *above* the cube with no shared coordinate system, so they collide. `--work-area-vertical-bias: 4` (style.css:24) shifts the work-area top-offset but not the hero, so it can't separate them. W3 S3 explicitly called for a "two-zone home layout" but on mobile it's still one overlapping zone.
Disposition: **BOOK**.
GESTALT fix — make home a real two-band vertical layout on mobile instead of two centered overlays. Give the home start-screen a *bottom-anchored* hero band and park the cube in the *upper* band: on `isHome`, set the stage's `place-items` to start-aligned with a top bias and constrain its `max-block-size` to ~`50dvh`, and re-anchor `EditorStartScreen` to the lower half (`align-self: end`, remove `top-0/mt-28` on mobile, use the work-area bottom band). Drive the cube's home-park translate with the same reduced-motion-aware spring from finding 1 so the cube *settles* into its upper park rather than jumping. On desktop the existing two-column split (headline left, cube right) already works (home-desktop.png is clean) — this only needs the mobile vertical split.

### 5. **[medium] Mobile dock exclusion zone is asymmetric and hard-coded, not derived — the cube/subject can graze the top dock band**
Evidence: TopDock sits at `top: calc(max(--work-area-top-offset, env(safe-area-inset-top)) + --dock-margin/4)` (`TopDock.vue:114`) and the mobile controls-pane reserves the top via `margin-top: calc(var(--dock-margin) + var(--dock-icon-height))` (`AnimationControlsGroup.vue:459`) — but the *stage row* (row 2) reserves nothing, so on a scene with no controls open the subject can render into the top dock band. The reserve constant `--dock-margin + --dock-icon-height` is duplicated inline rather than expressed as the matching top token to `--dock-menubar-reserve` from finding 2.
Disposition: **BOOK**.
GESTALT fix — symmetrize: introduce `--dock-topbar-reserve` (mirror of the new `--dock-menubar-reserve`) and apply both as `padding-block` on the mobile `.controls-layout` grid (`AnimationControlsGroup.vue:447`), so *every* row — controls pane AND stage — lives inside the dock-free band by construction. This closes W3 S5 ("reserve dock exclusion zones … so scene content can never render into the dock bands") structurally rather than per-row.

### 6. **[low] `--work-area-vertical-bias` is a magic divisor with no rhythm rationale; the work-area sits at an arbitrary ⅓-ish offset**
Evidence: `style.css:24-25`: `--work-area-vertical-bias: 4; --work-area-top-offset: max(calc((100dvh - --work-area-height) / 4), 0px)`. The comment says "¼ offset: positions work area above visual center for balanced feel," but the math is `slack/4` to the *top*, which only meaningfully biases when `--work-area-height < 100dvh` — on mobile `--work-area-max-height: clamp(44rem,94dvh,64rem)` (style.css:61) the slack is tiny, so the bias is near-zero where it's most needed (the home hero/cube collision in finding 4 is partly *because* the bias barely moves anything on mobile). It's a token shaped like rhythm but functionally inert on the viewports that need it.
Disposition: **RECORD**.
GESTALT fix — replace the divisor with an explicit optical-balance fraction that also feeds the home two-band split: define `--work-area-top-offset` and `--work-area-bottom-offset` as an *asymmetric* pair (e.g. top:bottom = 0.42:0.58 of slack) so the subject parks at the optical center (slightly above geometric center) consistently across viewports, and have the home hero/cube bands key off the *same* two offsets so spacing rhythm is one source of truth. Document the bias as a ratio token, not a divisor.
