# A.W1 — Design slice + release-CI repair (DEV→IMPL hinge)

The phase boundary. W1 is the last DEVELOPMENT wave and the first to touch ship-path
configuration: the design slice names the boundary-ergonomics and gate mechanisms W2–W4
implement, and the release-CI repair lands as the hinge—engine-code-free, mechanically
isolated (a `package.json` script split + workflow edits + a lockfile regen), and the
unblock that makes a clean-runner build—and therefore tag-release—possible for the first
time.

This wave establishes **inv β — the library build is glass-ui-free.** The publishable
artefact (`src/animation` → `dist/`) resolves zero `@mkbabb/glass-ui`; the `file:../glass-ui`
seam is demo-dev-only and never on the release path.

## The break

keyframes' CI ran `npm run build` = `vite build --mode production`, and `npm ci` resolved
the full dependency tree—including `"@mkbabb/glass-ui": "file:../glass-ui"`, which the demo
imports and the library never does. On a clean runner the sibling `../glass-ui` checkout is
absent, so `npm ci` cannot resolve the `file:` path and the install fails before any build
step runs. The library build (`src/animation/index.ts` → `dist/keyframes.js`) needs no
glass-ui at all—only `demo/` does—but the runner could not tell the two graphs apart, and
the publish leg was forced to a dev machine.

Two further snags compounded it. The whole-project type-check (`tsc --noEmit` over `src/` +
`demo/`) tripped on a demo-only `@mkbabb/glass-ui/dock` type gap, so `check` was red even
where the library itself was clean. And a duplicate `node.js.yml` workflow ran its own test
job plus a gh-pages deploy job that is structurally red on a clean runner—the demo build
needs the unpublished glass-ui sibling.

## What landed

### glass-ui → optionalDependencies + the glass-ui-absent lockfile

`@mkbabb/glass-ui` moves from `devDependencies` to `optionalDependencies` in `package.json`.
An optional dependency that fails to resolve is skipped, not fatal: on a clean runner where
`../glass-ui` is absent, `npm ci` walks past it and the install succeeds. The demo dev
machine—which has the sibling checkout—still resolves it through the `file:` symlink, so
local demo work is unaffected.

The lockfile is regenerated with glass-ui absent. This surfaces a subtlety the audit named:
`@popperjs/core` now records at the lockfile root (`package-lock.json:899`,
`node_modules/@popperjs/core`, v2.11.8, marked `dev`/`peer`) where it was formerly masked by
the glass-ui `file:` subtree. When glass-ui resolved through the symlink, its own dependency
subtree carried `@popperjs/core`, and npm deduped the demo's transitive use of it into that
subtree—so it never appeared as a root node. Drop the glass-ui subtree and the dedup target
vanishes, so the package hoists to the root. The regenerated lockfile is the honest
glass-ui-absent graph: it is what a clean runner actually installs, so it is what the lockfile
must pin.

### tsconfig.lib.json + check:lib

`tsconfig.lib.json` (new) extends `tsconfig.json` and narrows `include` to `["src/"]`—the
publishable surface only, never `demo/`. `check:lib` = `tsc --noEmit -p tsconfig.lib.json`
type-checks exactly that surface, dodging the demo-only `@mkbabb/glass-ui/dock` type gap that
broke the whole-project `check`. The whole-project `check` (`tsconfig.json`, `src/` + `demo/`)
stays for local demo development; the CI gate runs `check:lib`. inv β applies to the type-check
too: the check that gates the release path must itself be glass-ui-free.

### build:lib + the script split

`package.json` scripts gain three entries and repoint two:

- `+ check:lib` = `tsc --noEmit -p tsconfig.lib.json`
- `+ build:lib` = `vite build --mode production` — the library-only build (entry
  `src/animation/index.ts`; `production` mode in `vite.config.ts` already externals
  `vue`, `prettier`, `@mkbabb/parse-that`, `@mkbabb/value.js`; glass-ui is never imported by
  `src/`, so the library graph never touches it)
- `+ proof:boundary` = `node scripts/proof-boundary.mjs` (the gate mechanism named in the
  design slice; landed and wired in W3)
- `build` and `prepare` repoint to `npm run build:lib`

The split is the missing piece, not the outDir. `vite.config.ts` already routes the gh-pages
demo to a separate `dist/gh-pages/` outDir, so the two builds no longer share an
`emptyOutDir` target—the demo build cannot clobber `dist/keyframes.{js,d.ts}`. What was
missing was the *script* split so a runner builds the library without entering the demo graph.
`build:lib` is that script; the demo/gh-pages build stays a separate dev-machine arm the
release path does not require.

### ci.yml / release.yml repoint + provenance

Both workflows run the library-scoped gate in order:
`check:lib → build:lib → test → proof:boundary`. Every step touches only the publishable
surface; `npm ci` skips the optional glass-ui on a clean runner, so the whole sequence runs
glass-ui-free.

`release.yml` (tag-triggered on `v*.*.*`) re-runs that same gate before publishing, then adds:

- `permissions: id-token: write` (with `contents: read`)
- `npm publish --provenance --access public`

`--provenance` attaches a signed SLSA build-provenance attestation generated from the
workflow's OIDC identity—`id-token: write` is what mints that token. Publish auth stays the
`NPM_TOKEN` repository secret (`NODE_AUTH_TOKEN`); the OIDC token signs the attestation, the
npm token authenticates the publish. Two distinct credentials, two distinct jobs.

### node.js.yml retirement

`.github/workflows/node.js.yml` is removed (`git rm`). Its `test` job duplicated `ci.yml`'s,
and its `deploy` job ran `npm run gh-pages` + a `peaceiris/actions-gh-pages` publish—a demo
build that needs the unpublished glass-ui sibling and is therefore structurally red on a clean
runner. The demo gh-pages deploy is now a dev-machine action, not a CI job. Retiring the
workflow removes a permanently-red check and a redundant test run in one move.

### GitHub issue #1

The CI break is filed as GitHub issue #1—the real artefact replacing the audit's phantom
"#177" (a number with no corresponding issue). The tranche's CI-break finding now points at
a concrete tracker entry.

## Design slice (the DEV deliverable)

W1 names the mechanisms W2–W4 implement, each proven against the live source before it is
built:

- **`EasingResolvable` contract shape** — one shared string-easing-name resolver, value.js-free,
  proven against the three call sites (`numeric.ts`, `morph.ts`, `timeline.ts`). A free
  module, not a mixin or base class: the three consumers have no common ancestor, and a
  callable resolver composes by `has-a`, not `is-a`.
- **Silent-linear remediation** — eager-resolve-on-construct when the easing is a string name
  (the resolution kicks off in the constructor, as `Timeline` already did), with a dev-only
  `console.warn` for the residual same-tick synchronous `.at()`-before-resolution window. The
  trade-off recorded: eager-resolve does not reintroduce a static value.js edge—the
  `import("../engine")` stays dynamic; only its *trigger* moves earlier.
- **`build:lib` split** — spec'd against the live `vite.config.ts`: `production` mode, entry
  `src/animation/index.ts`, the existing `external` list. Landed in this wave.
- **`proof:boundary` mechanism** — a build-and-count gate: bundle a spring-only entry from
  source with rolldown (value.js + parse-that non-external), count value.js modules + static
  `engine.ts` edges in the entry chunk, fail on non-zero. Named here; landed in W3.
- **WAAPI `linear()` eligibility** — land-or-refute verdict: LAND. `springTimingFunction`
  carries its `springLinearStops()` `linear()` string; `waapi.ts` emits it as the WAAPI
  `easing` so a delegated spring runs the true curve on the compositor. Built in W4.

## Hard gate

A clean runner—`../glass-ui` absent—runs the full library sequence green with no `file:`
resolution:

```sh
npm ci && npm run check:lib && npm run build:lib && npm test && npm run proof:boundary
```

`npm ci` skips the optional glass-ui; `check:lib` type-checks `src/` only; `build:lib`
externals value.js + parse-that and never enters the demo graph; `test` (vitest, jsdom)
imports no glass-ui; `proof:boundary` confirms the value.js boundary holds. inv β is met:
the publishable artefact resolves zero `@mkbabb/glass-ui`.

**Empirical verification.** The gate was run against a full repo copy to `/tmp` with
`../glass-ui` absent—reproducing a clean runner's filesystem exactly—and went green end to
end. The `file:../glass-ui` seam is confirmed demo-dev-only and off the release path.

## Disposition

LANDED. `tsconfig.lib.json`, the `package.json` script split + glass-ui→optionalDependencies
move, the glass-ui-absent lockfile regen, `ci.yml`/`release.yml` repoint + provenance, and the
`node.js.yml` retirement all ship in this wave. inv β realized; GitHub issue #1 filed. The
design slice's named mechanisms (`EasingResolvable`, eager-resolve + dev-warn, `proof:boundary`,
WAAPI `linear()`) carry forward as the binding specs for W2–W4. The dev/impl boundary lands at
this wave's close.
