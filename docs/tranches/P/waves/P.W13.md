# P.W13 — the emerging-CSS resolution pass (`resolve-values.ts`): if() · @function · spring() · sibling-index() lowered to concrete animatable values

**Band:** B — Engine (feature) · the "lead the platform" capability.
**Phase:** **NOW** for the element-INDEPENDENT arm — `if(supports/media)` + `spring()` (value.js ALREADY parses both — `parsing/index.ts:310` / `parsing/easing.ts:184`); **element-DEPENDENT (Phase 2)** for `if(style(--p))` + `sibling-index()`/`sibling-count()` (require the target element, absent at the flatten seam); **value.js-P-gated** for `@function` call-inlining (gated on TWO items — see below).
**Sequence:** `P.W1 apparatus ─► P.W13` (consumes the resolve seam); independent of P.W2/P.W3 (a different concern — value lowering, not blend/egress). Researched 2026-06-22 (`docs/tranches/P/EMERGING-CSS-RESEARCH.md`); full-loop RE-SCOPE applied (`docs/tranches/P/FULL-LOOP-LEDGER.md` P.W13-emerging).
**Owning-idea:** the owner directive (2026-06-22) — **novel CSS features SHOULD be supported in our grammar + engine; the library LEADS the platform, browsers catch up.** The precedent is `springTimingFunction`/`springLinearStops`: the engine already computes a value (a spring `linear()`) the platform lacks. This wave generalizes that to one compile-time lowering pass.

## Why (the grounded capability — NOT a contrivance)

The contrivance smell-test's "speculative dependency" clause does **not** apply to a grammar+engine library proactively supporting standardized + emerging CSS — that is the library's *remit*. And the parser side is **largely already shipped** (value.js O.W4): the net-new work is a self-contained kf lowering pass, mirroring an existing pattern. Three of the four features are real, Chromium-shipped CSS today (`if()` Chrome 137, `@function` Chrome 139, `sibling-index()` Chrome Canary; `spring()` WebKit-only). kf resolving them at compile time makes that CSS animate in **every** browser — exactly as `springLinearStops` gives every browser a spring via `linear()`.

## The seam + the module (the gestalt — ONE pass, TWO call sites by element-dependence)

**The RE-SCOPE correction (full-loop ledger line 353):** the original spec framed this as ONE seam (`resolveKeyframes → flatten`). That is wrong — `resolveKeyframes(input: string | Stylesheet)` (`adapter.ts:175`) takes ONLY a string/Stylesheet; it has **NO element/target context at flatten time** (confirmed: it never sees the target). So the unified `resolveValues` rewriter runs at **TWO call sites, split by element-dependence**, NOT one:

- **Phase 1 — element-INDEPENDENT (NOW, in-realm), at the `resolveKeyframes → flatten` seam:** `if(supports(...))` / `if(media(...))` and `spring()`. These resolve with zero target context (CSS.supports / matchMedia / the kf physics), so they lower at flatten time exactly as the gestalt intends — the frame pair holds two concrete values and **interpolation runs exactly as today** (zero hot-path change).
- **Phase 2 — element-DEPENDENT (post-`setTargets`), against the resolved target:** `if(style(--p))` (reads a resolved custom-prop off the element), `sibling-index()`, `sibling-count()` (DOM sibling position). These CANNOT resolve at the string seam (no element exists there); they run in a second pass once the animation has its target.

It is still ONE rewriter module (the gestalt holds — not four per-feature hacks); it is invoked at two lifecycle points. `ctx.env` is threaded by injection exactly as `ScrollTimeline` injects `getScrollY`/`getViewportHeight` (`timeline.ts`), and defaults to SSR-safe no-ops (`supports → false`, `matchMedia → {matches:false}`) so a server compile picks the else-branch deterministically.

**New module `src/animation/resolve-values.ts` (HEAVY — imports value.js `FunctionValue`/`ValueUnit`):**
```
resolveValues(value, ctx) -> same node types (ValueArray | FunctionValue | ValueUnit)
  ctx = { functions: Map<name,CustomFunctionDescriptor>, properties: Map, env: { matchMedia?, supports?, customProps?, siblingIndex?, siblingCount? }, seen: Set, depth }
```
A recursive rewriter that, per `FunctionValue.name`:
- **`if`** (the 2-branch `supports`/`media` case is **Phase 1, NOW**; `style(--p)` is **Phase 2**) — the condition strings arrive as OPAQUE VERBATIM text (`'supports(color: lch(0 0 0))'`), so kf **re-parses each condition with value.js's own `parseCSSValue`** (no hand-rolled cond parser — `supports(...)`/`media(...)` both round-trip) and evaluates: `supports(...)`→`CSS.supports` (sync, SSR-safe), `media(...)`→`matchMedia(...).matches` (the engine already uses `matchMedia` in `smooth.ts:27`/`spring.ts:160`); first-true wins; `else` is the fallback; **no-branch-no-else → guaranteed-invalid → drop the declaration** (do NOT emit empty-string — it would corrupt interpolation; this DROP is gated explicitly). Re-resolve on a `matchMedia('change')` (the `layoutEpoch` re-resolution model already exists for `cq*`). `if(style(--p: v))` reads a resolved custom-prop OFF the element → **Phase 2 (element-aware)**. **Multi-branch (>2 clauses) is a value.js follow-up** — value.js's `if()` producer is confirmed lossy today (it collapses 3 clauses to first-consequent + else, dropping the middle); the common 2-branch case ships NOW.
- **`spring(mass stiffness damping velocity)`** (**Phase 1, NOW — the FIRST/lowest-effort arm; see the spring() ADOPT note below**) — `springCssToOptions(m,k,c,v0)` → `{ response: 2π·√(m/k), dampingFraction: c/(2·√(k·m)), initialVelocity: v0 }` → the EXISTING `SpringProgress`/`springTimingFunction` (kf already owns the physics). **kf OWNS validation + defaults-fill** (`mass>0`, `stiffness>0`, `damping≥0`, default `1/100/10/0`): value.js parses `spring(...)` via its GENERIC function parser (NOT `parseSpring`, which throws on space-separated input and is comma-only/brittle — confirmed), so the generic path provides no validation. The settle horizon is fixed at `maxDuration = response·4` (the kf default), a deliberate self-consistent choice — **NOT WebKit native-parity** (CSS `spring()` carries no duration; the normalized curve shape depends entirely on the settle-horizon, so native parity is unattainable as a gate assertion — measured `maxDiff≈0.47` against the WebKit linear() twin). HW-accel is INHERITED via the existing `linear()` twin (the CE-1.0 rule), no new wiring.
- **`--foo(args)`** (a dashed-function `@function` call — **value.js-P-gated on TWO items; sequence LAST**) — bind the descriptor's params to the args (default → guaranteed-invalid order), substitute into the `result` expression, evaluate nested `calc`/`if`, return the concrete value. Cycle-guarded by `seen`. **kf authors nothing here until value.js-P publishes the dashed-function-CALL parse arm** (`--ident(args) → FunctionValue('--ident', [args])`) AND `extractFunctions()` — confirmed the call site does NOT parse today (`--double(2)` → a bare `ValueUnit`, args dropped, name undefined), so this arm is genuinely MEASURE-FIRST-blocked on the sibling publish (inv-16).
- **`sibling-index()` / `sibling-count()`** (**Phase 2, element-aware; LOW effort**) — read the element's 1-based index / sibling total post-`setTargets` → an integer `ValueUnit`, fed into `stagger` (the natural consumer). PARSE is already free via value.js's generic `FunctionValue` producer (confirmed: both → `FunctionValue('sibling-index'/'sibling-count', [])`) — so **NO value.js-P parse-arm ask** (drop it; the only value.js nicety would be arg-count validation, not blocking).

- **`sibling-index()`/`sibling-count()` are NOT value.js-P-gated for parsing** (full-loop correction, ledger line 401) — value.js's generic `FunctionValue` producer already yields `FunctionValue('sibling-index'/'sibling-count', [])` (confirmed). **DROP the `sibling-*` parse-arm ask** from the dispatch; the only value.js nicety would be arg-count validation (not blocking). - The if() **multi-branch** (>2 clauses) is a value.js follow-up — value.js's producer is confirmed lossy today (3 clauses → first-consequent + else, middle dropped); the common 2-branch case ships NOW.
