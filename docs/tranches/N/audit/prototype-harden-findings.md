### Issues
- **[high]** LIGHT-MODE CONTRAST FAILURE. In light theme the --ink token flips to near-black (nameplate name color = oklch(0.22 0.02 268), arrow glyph color = same, index = oklch(0.42)), but the stage void is theme-invariant dark (oklch(0.13 0.012 270)). Result: the scene name, the n/7 index, and the arrow chevrons are dark-on-dark — effectively invisible / WCAG-failing in light mode (visible in screenshot 07-stage-light-mode.png: arrows are black circles, the nameplate text/index vanish). This violates locked decision 4's intent ('the void stays dark in BOTH themes; only the cards/arrows pick up the light/dark specular cohort') — the glass-chrome FOREGROUND ink must NOT flip to dark over the constant-dark void. The synthesis even flags 'still reads in light mode' as the open TASTE question; the prototype currently does not. Fix: pin the on-stage text/glyph color to a light ink regardless of theme (the void is dark in both themes, so its content must be light in both), and let only the specular cohort swing.
- **[med]** MOBILE LAYOUT BROKEN at 390px. Measured: console.bottom (793) > stage-hint.top (771) so the controls overlap the keyboard-hint strip, AND the next-arrow wraps below the nameplate (arrowWrapped true) — verified in screenshot 10-mobile-open.png where the next chevron, nameplate, and hint text collide into an unreadable stack and the ring flanks are clipped hard at the viewport edges. The @media(max-width:720px) rule only tightens the ring radius + adds flex-wrap:wrap, which is what causes the wrap/overlap. The research itself lists 'phone-narrow layout' as an open question; the prototype's bottom-anchored console + wrap is not a usable phone layout. Production needs the flagged dedicated phone-narrow flat-carousel, not just a radius tweak.
- **[med]** TOOLBAR UNREACHABLE WHILE STAGE OPEN. The .toolbar (Theme + Reduce-motion toggles, z-index:5) lives in the normal layer; the stage is a Popover-API top-layer element which paints ABOVE all normal-layer z-index. Hit test at the toggle's center while open returns 'stage-3d', not the button — a real pointer cannot reach the toggles once the stage is open (I had to dispatch synthetic click events to exercise them). In the prototype these are demo-only controls (so lower impact), but it is a genuine top-layer gotcha to record: any chrome that must remain operable over a top-layer popover has to itself be in the top layer (its own popover) or inside the stage.
- **[low]** The dropdown->stage shared-element morph (research beat: morph the dock-trigger label into the stage nameplate) is NOT wired — the trigger carries view-transition-name:dock-select-trigger while the nameplate carries stage-nameplate (distinct names), so the open VT only blooms stage-root opacity 0->1; there is no trigger->nameplate morph. Acceptable per the prototype's stated divergences, but the 'grows from the dropdown' liquid-glass beat is therefore not actually demonstrated — only a fade-bloom is.
- **[low]** AESTHETIC: the cone reads slightly hard/flat at the top edge and the whole shaft is a fairly uniform grey trapezoid rather than the soft, vaporous, top-narrow volumetric beam of the DK64 reference. The mask-image edge feather + blur(3px) soften the left/right edges but the top is still a crisp horizontal cut, and the dust-grain (::after) is barely perceptible. Also the second flanks (Square/Sequence at opacity 0.327, brightness 0.55, blur ~5px) are dimmed aggressively enough that they barely register as 'living previews' — the '5 visible' count is technically met but reads closer to 3-visible. Both are subtle polish items, not blockers.
