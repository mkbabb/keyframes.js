# B.W6 — Perfected CI (inv γ + δ + boundary + lockfile)

CI's job in keyframes.js is to make the un-shippable un-mergeable. A's library-scoped
chain (`check:lib → build:lib → test → proof:boundary`) did that for the publishable
artefact and nothing else, which is exactly how a 698-byte blank gh-pages build, four
empty scenes, a cube clipped off the right edge, and a boundary gate that proves one of
seven light entry points all reached master under a green check. W6 closes the gap: the
demo cannot ship blank (inv γ), no page occludes on any viewport (inv δ wired), the
boundary gate proves every light entry, the lockfile matches the inv-β prose it is
supposed to anchor, and the before/after-every-page edict runs as a gate rather than a
custom. After W6 the green check means *the whole product is true*, not just `dist/`.

This is the gates wave. It owns no engine or demo behavior — W2 transposes the engine,
W3 makes the scenes paint and fit, W4 repairs the prod build. W6 takes the artefacts those
waves produce (the widened boundary script, the occlusion harness, the repaired entry, the
capture harness) and binds each into `ci.yml` / `release.yml` so a regression in any of them
turns the check red. It rides last among the impl waves for that reason — every gate it
wires needs its subject to exist first.

## § Goal

**What lands.** Five gates and two hygiene bumps, all in `.github/workflows/` + `package.json`
scripts + `scripts/`:

1. **inv γ — the demo cannot ship blank.** A `demo-smoke` CI job runs `npm run gh-pages` against
   a resolvable glass-ui and asserts the built `dist/gh-pages/index.html` carries a non-trivial
   app entry that *mounts* — a tree-shaken/blank build fails CI. *Why:* the single most
   user-visible defect A's library-first scope shipped was a deployable that paints nothing
   (design audit BLOCKER); no gate caught it because `ci.yml` builds only the library.

2. **inv δ — no page occludes on any viewport.** The scripted Playwright occlusion gate (zero
   viewport overflow, zero dock-over-content overlap, every scene subject visible at idle) runs
   in CI across every page × {375, 1280, 1440}. *Why:* the occlusion set (cube off the right
   edge, hero over the cube, dock flush at y=0, four blank scenes) was found by a scripted sweep
   that lived only on a dev machine; a gate makes the regression class permanent-caught.

3. **`proof:boundary` proves every light entry, not just `SpringProgress`.** *Why:* the gate as A
   shipped it builds a spring-only entry, so a static value.js edge in `smooth`/`numeric`/`morph`/
   `timeline` that the spring graph does not transitively reach passes GREEN (plan audit [high]).

4. **The lockfile matches inv β's prose.** The committed lockfile is glass-ui-*present*; FINAL.md
   claims "regenerated glass-ui-absent." W6 makes the artefact true to the claim (or the claim true
   to the artefact) and proves it with a `/tmp` clean-runner archive run. *Why:* inv β currently
   survives on `optional:true` skipping a dangling link, not on an absent graph — a fragile
   coincidence the prose mis-describes.

5. **The before/after π gate is wired.** The capture harness (`audit/`, authored at W0) runs at
   tranche open and close as a real step, with full visual binding now that browser tooling is
   available. *Why:* B authored the before/after-every-page edict into precepts; the authoring
   tranche must run it as a gate, not narrate it.

**Hygiene.** `actions/checkout` + `actions/setup-node` bump `@v4 → @v5` (the v4 line ships on the
deprecated node20 actions runtime). The dep-regression gate from W1 — the demo/tooling bump must
keep the full chain green — is recorded here as the standing CI shape it produces.

**Why it matters.** Every defect B repairs is a defect that reached production under a passing
check. W6 is the forcing function that makes each repair *stay* repaired: a blank build, an
occluded page, an unproven boundary edge, and a lockfile/prose drift each become a red check, not
a future audit finding.

## § Scope

### γ — the demo-build smoke gate (`ci.yml` + `scripts/demo-smoke.mjs`)

`ci.yml:43-44` runs only `build (library) → npm run build:lib`. The gh-pages build
(`package.json:40`, `vite build --mode gh-pages`) has **no gate** — design audit names this
exactly: "gh-pages prod build has no CI gate — the broken build can ship silently on a manual
deploy." W6 adds a job, separate from the library gate (the library gate must stay glass-ui-free
per inv β; the demo build legitimately needs glass-ui):

```yaml
demo-smoke:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
        - uses: actions/checkout@v5
        - uses: actions/setup-node@v5
          with: { node-version: 24, cache: "npm" }
        - run: npm ci
        # glass-ui resolvable for the demo arm: install the published package
        # (or check out the sibling) so `npm run gh-pages` builds the real app graph.
        - run: npm run gh-pages
        - run: node scripts/demo-smoke.mjs
```

`scripts/demo-smoke.mjs` (new) asserts against the **built** `dist/gh-pages/index.html` — the same
artefact a deploy would publish — three conditions that a blank/tree-shaken build fails:

- **A real app entry exists.** The HTML references a built module entry whose emitted chunk is
  non-trivial (a byte floor well above the 698-byte preload-shim the broken build emitted — gate
  the *entry chunk's* size, not `index.html`'s, so a future shim can't pass by inlining). *Gestalt:*
  the failure mode was rolldown tree-shaking the inline `<script type="module">` bootstrap out of
  `demo/app/index.html:38-46`; W4 extracts it to a referenced `demo/app/main.ts`, and this gate
  asserts that extraction stays load-bearing — the entry must be *referenced and substantial*, not
  merely present.
- **CSS is emitted and wired.** The build emits an `index-*.css` and `index.html` carries the
  critical-CSS apparatus (`vite.config.ts:44-129`) it currently no-ops on (design audit: "Critical-CSS
  / instant-paint apparatus is well-designed but currently dead … the broken build emits no CSS").
  Assert the `<style data-critical>` block + the deferred `<link … media="print" onload>` are present.
- **The app mounts.** Serve `dist/gh-pages/` headless, load `/`, and assert `#app` has non-trivial
  child content after mount (the blank build leaves `#app` empty). This is the "paints" half — a
  build that emits an entry but throws on mount still fails. Reuse the Playwright harness inv δ
  installs, so γ and δ share one browser dependency.

*Why a byte floor AND a mount check:* a size assertion alone is satisfiable by a bloated-but-broken
bundle; a mount assertion alone is satisfiable by a hand-written placeholder. Both together bind the
actual invariant — *a real app that renders*.

### δ — the occlusion gate wired into CI (`ci.yml` + `scripts/occlusion-gate.mjs`)

The occlusion sweep that produced `audit/occlusion-report.json` (W0) is a dev-machine script today.
W6 promotes it to a CI job that fails on any non-empty `offscreen`/`dockOverlaps`/clipped-subject
finding. The report schema is already the gate's assertion surface — each scene record carries
`scrollOverflow`, `clipped[]`, `offscreen[]`, `dockOverlaps[]`. The gate iterates every
page × {375, 1280, 1440} and fails when:

- `scrollOverflow.x !== 0` (horizontal overflow — the cube clipping the right edge produced exactly
  this class on home/cube laptop+desktop, `occlusion-report.json` entries `home/laptop`, `cube/desktop`),
- any `dockOverlaps[]` is non-empty (dock-over-content — the y=0 top-dock flush + bottom transport
  over the cube), or
- a scene's **subject is absent** (the four blank scenes report `clipped:[]`/`offscreen:[]` only because
  there is nothing to clip — W3 seeds each subject; the gate asserts a known per-scene subject selector
  has a non-zero in-bounds rect, so "clean because empty" can no longer pass).

*Gestalt:* the W0 report's "amiga/square/easing/spring clean" rows are false-greens — empty viewports
register zero overflow. The gate must distinguish *occlusion-free because fitted* from *occlusion-free
because blank*; the per-scene subject-present assertion is the discriminator, and it is the same
assertion the before/after π gate makes (the subject renders), so δ and π share the subject manifest.
This also retires the CHRONIC Playwright >50ms-trace stub (`bench/playwright.bench.ts:1-42`,
`expect(true).toBe(true)`) by replacing the stub with a real Playwright-backed CI gate — the trace half
of that chronic lands in W3/W7's harness; W6 wires the occlusion half here.

`axis-line` strays (`div.axis-line.{x,y,z}` overflowing every cube/home record by thousands of px) are
**excluded from the gate** — they are decorative guide-lines W3 fades/hides at the edges (design audit
LOW), not content occlusion. The gate's clipped-subject check targets the named scene subjects, not the
axis guides; record the exclusion in `scripts/occlusion-gate.mjs`'s header so a future reader does not
read the guide-lines as a missed regression.

### proof:boundary — all light entries (`scripts/proof-boundary.mjs`, rides W2)

W2 widens `scripts/proof-boundary.mjs` from the single spring-only entry (`:49-51` builds
`import { SpringProgress } …`) to **every light export off `index.ts:30-48`** —
`NumericAnimation`, `SmoothProgress`, `SpringProgress`, `springLinearStops`,
`springTimingFunction`, `ElementMorph`, `Timeline`/`ScrollTimeline`/`ManualTimeline`,
`RAFPlayback`. W6 binds the widened gate as the CI condition and hardens its construction
so the proof is airtight (plan audit [high] enumerates the four gaps):

- **Per-entry negative coverage.** Bundle each light export as its own entry (or one entry per
  module) and assert 0 value.js modules + 0 static `engine.ts` edge per entry — so a static
  value.js edge reachable from `numeric.ts` but not `spring.ts` turns the gate red where today
  it passes GREEN.
- **Empty node_modules allowlist for value.js + parse-that.** They stay NON-external
  (`proof-boundary.mjs:60-62`) so a reintroduced static edge bundles their source into the entry
  chunk where the count catches it — this is correct and W2 keeps it; W6 asserts the construction
  holds for *every* entry, not just the spring one.
- **Assert the heavy engine lands in a non-entry dynamic chunk.** Today the gate checks `engine.ts`
  is *absent* from the static set; widen it to also assert it is *present as a dynamic chunk* — so a
  build that accidentally drops the dynamic boundary (eager-importing the engine, or tree-shaking the
  `loadAnimationEngine()` accessor away) is caught, not silently passed.
- **Post-build dist-grep complement.** Add a second, cheap check that greps the light modules' *source*
  import statements for any static `from "@mkbabb/value.js"` specifier (plan audit [low]: the dead
  `void _probe` import class) — catching a dead-but-armed static edge before it becomes reachable, which
  the bundle-graph count cannot see by construction.

W6 records the proof in `proof-boundary.mjs`'s header that a passing gate means "no *reachable* static
value.js edge from any *enumerated* light entry," and that the entry list must track `index.ts:30-48` —
a new light export without a corresponding proof entry is itself a gate failure (assert the entry set
equals the barrel's light export set, so adding a light export without proving it cannot pass).

### Lockfile reconciliation + clean-runner verify (`package-lock.json`, FINAL.md)

The committed lockfile is glass-ui-*present*: `package-lock.json:849-851` records
`node_modules/@mkbabb/glass-ui` as a `{ "resolved": "../glass-ui", "link": true }` symlink, and
`package.json:64-65` keeps `"@mkbabb/glass-ui": "file:../glass-ui"` in `optionalDependencies`. FINAL.md:113
and the W1 wave spec (A.W1 "What landed → the glass-ui-absent lockfile") assert the lockfile was
*regenerated with glass-ui absent*. These contradict (plan audit [high] inv-β + [medium] plan-fidelity).
inv β survives in CI only because `optional:true` (the root `../glass-ui` node, `package-lock.json:67-69`)
lets `npm ci` walk past the dangling sibling on a clean runner — a *skip*, not an *absence*. W6 resolves
the contradiction one of two ways, RESOLVED to (a):

- **(a) Regenerate genuinely glass-ui-absent (RESOLVED).** Remove `../glass-ui` from the install root,
  `npm install` to regenerate the lockfile against a tree with no sibling checkout, and commit the
  glass-ui-free lockfile — so the committed artefact is the graph a clean runner actually installs. The
  `@popperjs/core` root-hoist A.W1 already documented (the dedup target vanishes when the glass-ui subtree
  is dropped) confirms the regen is the honest graph. inv β then holds on *absence*, not on a skip.
- **(b) Correct the prose (fallback, only if (a) breaks the demo dev install).** State the honest reality
  in FINAL.md: glass-ui is recorded-but-optional; the clean runner skips it via `optional:true`. Reserved
  only if regenerating absent destabilizes the `file:` demo workflow — (a) is the no-legacy move and is
  preferred.

Either way, verify with a **`/tmp` clean-runner archive run** at the inv-β / π floor — the same protocol
A.W1's hard gate used (a full repo copy to `/tmp` with `../glass-ui` absent), run end to end:

```sh
# in a /tmp archive copy, ../glass-ui absent:
npm ci && npm run check:lib && npm run build:lib && npm test && npm run proof:boundary
```

Green confirms the committed lockfile installs glass-ui-free on a runner with no sibling, closing the
gap between the artefact and the inv-β prose that anchors it.

## § Design decisions

1. **`demo-smoke` is a separate job, not a step in the library gate (RESOLVED).** The library gate must stay
   glass-ui-free (inv β); the demo build legitimately needs glass-ui. A shared job would either pull glass-ui
   into the library gate (violating inv β) or skip the demo build (defeating inv γ). Two jobs, two dependency
   postures — the library job runs glass-ui-absent on a clean runner; the demo job installs a resolvable
   glass-ui. *Trade-off:* the demo job depends on glass-ui being installable in CI (published package or sibling
   checkout); this is acceptable because inv γ is a demo invariant, and the demo's whole purpose is to consume
   glass-ui. The release path (`release.yml`) does NOT gain `demo-smoke` — releases publish the library, not the
   demo, so the release gate stays the pure library chain.

2. **The byte floor gates the entry *chunk*, not `index.html` (RESOLVED).** The broken build's 698 bytes were
   `index.html` itself (a preload shim). A naive `index.html`-size floor is defeated by a future shim that inlines
   bloat. Gating the *referenced entry chunk's* size — plus the mount assertion — binds the real invariant: a
   substantial app module that renders. *Trade-off:* the gate must parse `index.html` to find the entry reference;
   this couples it to the build's HTML shape, which is acceptable because that shape is exactly what inv γ protects.

3. **The occlusion gate needs a subject manifest, not just the overflow report (RESOLVED).** The W0 report's
   "amiga/square/easing/spring clean" rows are false-greens — an empty viewport has nothing to overflow. The gate
   therefore carries a per-scene subject selector manifest and asserts each subject has a non-zero in-bounds rect,
   so "occlusion-free because blank" cannot pass. This manifest is *shared with the π gate* (the subject the
   occlusion gate fits is the subject the π gate paints) — one source of truth, two assertions. *Trade-off:* the
   manifest must track the demo's scene structure; W3 owns the subjects, W6 owns the manifest's gate role, and the
   shared use keeps them from drifting.

4. **Lockfile disposition (a) — regenerate glass-ui-absent — is the no-legacy choice (RESOLVED).** Correcting the
   prose (disposition (b)) leaves the artefact and its anchoring invariant describing different graphs forever; the
   user's no-legacy mandate prefers the artefact made true. (b) is reserved strictly for the case where regenerating
   absent destabilizes the `file:` demo dev install — a contingency, not the plan. The `/tmp` clean-runner verify is
   the proof either disposition must pass.

5. **The widened `proof:boundary` asserts its entry set *equals* the barrel's light export set (RESOLVED).** A new
   light export added to `index.ts:30-48` without a corresponding proof entry is itself a gate failure — otherwise
   the coverage hole A left (entries drift behind the barrel) silently reopens. The gate's entry list is derived
   from / checked against the barrel, not hand-maintained, so the all-entries property is self-enforcing. *Trade-off:*
   the gate reads `index.ts`'s light export set; this couples it to the barrel, which is correct — the barrel *is* the
   boundary the gate proves.

6. **W6 wires gates; it does not author behavior (RESOLVED).** Every subject W6 gates is produced by an earlier wave
   — the repaired entry (W4), the fitted/painted scenes (W3), the widened boundary script (W2), the capture harness
   (W0). W6 holds zero engine or demo source; it is `.github/workflows/` + `scripts/` + `package.json` only. This is
   why W6 rides last among the impl waves: a gate cannot be wired before its subject exists. *Trade-off:* W6 cannot
   land before W2/W3/W4; the DAG (B.md §Wave table) sequences it accordingly.
