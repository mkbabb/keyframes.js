# B.W4 — Loading perf (prod build + splash + lazy)

Phase: IMPL (authored-now-run-later). DAG: rides after B.W1 (the modern dep
baseline); is prerequisite to B.W7's authoritative perf re-measure (the dev-mode
lighthouse numbers below are not a baseline you can improve against — they are a
broken build measuring nothing). File-disjoint from B.W2 (engine) and B.W3
(scene/occlusion); touches `demo/app/index.html`, a new `demo/app/main.ts`, the
two static-heavy import sites, and a dev-only LoAF observer module — nothing the
sibling demo waves own.

## § Goal

keyframes.js' shop-window **paints in production**, and paints **instantly**.

Today the deployed demo paints nothing. `vite build --mode gh-pages` emits an
entry chunk that is a 698-byte no-op — the entire Vue application, its router,
and every byte of CSS were tree-shaken out of the build, so the gh-pages site
loads, runs a modulepreload polyfill, and stops. The only thing the visitor sees
is a hardcoded `keyframes.js` splash that the (never-mounting) app was supposed to
replace. The engine that animates anything cannot animate its own front door.

W4 lands four things, each WHAT+WHY:

1. **A real app entry.** Extract the inline bootstrap to `demo/app/main.ts`
   referenced by `<script src>`, so rolldown sees a true module-graph root and
   keeps the app — *because an inline `<script type="module">` is a leaf rolldown
   is free to eliminate, and it did.*
2. **Instant first paint.** Delete the `.loading-skeleton` `keyframes.js` splash;
   the genuinely-critical first-paint CSS already lives in `criticalCSSPlugin`
   (dead today because no CSS emits) and lights up the moment the entry is real —
   *because the splash is an off-token content-swap flash that does not match the
   real top-left hero, and the app should paint its own first frame, not a
   placeholder it then overwrites.*
3. **Heavy chunks off the critical path.** monaco and three load lazily, behind
   the scenes/editor that need them — *because a 3.7 MB editor and a 3D library
   must never sit between the visitor and the home hero.*
4. **Causal perf evidence.** Wire the chronic LoAF observer (dev-only,
   feature-detected) as the attribution source for the prod-perf measurement and
   the demo bench — *because A's `scheduler.yield()` jank claim has been
   eyeball-only across two tranches for want of exactly this consumer, and the
   real lighthouse run can only be authored once the build paints.*

The headline `keyframes.js` is the engine made true on its own page: it loads
fast, paints instantly, and the heavy machinery arrives on demand.

## § Scope

### 1 — FIX the broken prod build (root-caused, the wave's first step)

**Confirmed root cause (on disk, this audit).** The built
`dist/gh-pages/assets/index-Dezn_h7o.js` is **exactly 698 bytes** and contains
*only* the Vite modulepreload-polyfill IIFE — no `createApp`, no `App.vue`, no
router import. **No `.css` asset is emitted at all** (`dist/gh-pages/assets/`
holds only the two monaco workers `editor.worker` + `css.worker`, the codicon
font, and image assets). The built `dist/gh-pages/index.html` references that
698-byte shim as its sole entry (`<script type="module" crossorigin
src="./assets/index-Dezn_h7o.js">`) and still carries the loading skeleton in its
`<body>`. The deployed page therefore paints the splash and mounts nothing.

The cause is `demo/app/index.html:38-46` — an **inline** `<script type="module">`
that is the *only* importer of `App.vue`, `router`, and the CSS cascade:

```html
<script type="module">
    import { createApp } from "vue";
    import App from "./App.vue";
    import { router } from "./router";
    const app = createApp(App);
    app.use(router);
    app.mount("#app");
</script>
```

Rolldown (vite-8) treats an inline module as a graph *leaf* with no exports and
no live side-effecting reference it is required to preserve, and DCEs its body.
What survives is the preload polyfill the bundler injects unconditionally — the
698-byte shim. Every transitive import (the app, the router, the entire CSS) dies
with the body.

**The fix — extract to a real entry module.**

- **Create `demo/app/main.ts`** holding the bootstrap verbatim:
  ```ts
  import { createApp } from "vue";
  import App from "./App.vue";
  import { router } from "./router";
  // The demo's CSS cascade enters the graph through main.ts so rolldown keeps
  // it as a true entry import (the criticalCSSPlugin matches the emitted
  // index-*.css asset; today that asset does not exist because nothing imports
  // the cascade through a retained entry).
  import "@styles/style.css";
  import "@styles/utils.css";

  const app = createApp(App);
  app.use(router);
  app.mount("#app");
  ```
  *Gestalt rationale:* the entry is now a named file rolldown resolves as a
  module-graph root — not an inline leaf it may eliminate. The CSS imports move
  into the entry (rather than being implied by Vue SFC `<style>` blocks alone) so
  the bundle deterministically emits the `index-*.css` asset
  `criticalCSSPlugin` (`vite.config.ts:44-129`) and `deferLazyCSSPlugin`
  (`vite.config.ts:15-32`) both match by name — the well-designed but currently
  dead critical-CSS apparatus comes alive the instant a real CSS asset exists.
  (Confirm the exact CSS entry points by matching the dev-mode graph; whichever
  stylesheet the dev `index.html`/SFCs pull in becomes the explicit `main.ts`
  import so dev and prod resolve identically — no `dist/` alias, no self-alias,
  per `vite.config.ts:138-153`.)

- **Reference it from `demo/app/index.html`** — replace `:38-46` with a single
  `<script type="module" src="./main.ts"></script>`. Vite/rolldown promote a
  `<script src>` pointing at a first-party module to a true HTML entry; it is not
  DCE-eligible. This is the one-line change that turns a 698-byte shim into a real
  application bundle.

- **No `manualChunks` change is required for the entry.** The existing
  `manualChunks` (`vite.config.ts:253-262`) and the `modulePreload`
  `resolveDependencies` exclusion (`:242-249`) already split vendor chunks
  correctly — they were simply never reached because there was no entry to chunk
  *from*. With a real entry, the existing split produces a real `vendor-*` set +
  an `index-*.js` app chunk + an `index-*.css` asset.

### 2 — REMOVE the splash, instant-paint via critical CSS

**Delete the `.loading-skeleton` block** at `demo/app/index.html:50-80` — the
`#app` wrapper's inline `<style>` (`:53-77`) and the `<div class="loading-skeleton">`
`keyframes.js` title (`:78-79`). Leave `#app` empty:

```html
<body>
    <div id="app"></div>
</body>
```

*Gestalt rationale (design-findings blocker + 4 HIGH/MED siblings).* The splash is
a centered bold `keyframes.js` (`index.html:68-73`, bespoke off-ladder
`clamp(2.5rem,6vw,5rem)` bold Instrument Serif) that does **not** match the real
home hero — the top-left `Select an animation` start screen
(`EditorStartScreen.vue`). When the app mounts it content-swaps the centered
splash for a top-left hero: a flash, not a handoff. It also hardcodes off-token
colors (`#1a1a1a/#fff/#0a0a0a/#e5e5e5`, `index.html:53-80`) that drift from the
warm-cream design tokens. The user's stated goal is its removal.

Instant first paint comes from `criticalCSSPlugin` (`vite.config.ts:73-114`),
which inlines the resolved `--background`/`--foreground`/color-scheme/body-reset
tokens as `<style data-critical>` and defers the main stylesheet
(`media="print" onload`). Once the entry emits a real `index-*.css`, the plugin
matches `index-*.css` in the bundle (`vite.config.ts:55-61, 117-119`), inlines
the critical block, and the first paint is the correctly-themed background +
geometry — no JS, no font, no flash. The `#app` then mounts the genuine first
frame (the hero) directly onto that painted ground. **No placeholder content** —
the engine paints its own first frame, which is the whole point of a demo for an
animation engine.

*Why not keep a minimal placeholder:* a placeholder that is not the real hero is
the very content-swap the finding flags. Instant-paint critical CSS gives a
themed, layout-stable ground with zero CLS (the audit already measures CLS
0.006-0.01); the hero arrives as the app's true first frame, so there is nothing
to swap.

### 3 — Lazy-load monaco + three (close the static-import leaks)

The vendor-split scaffolding is already correct — what defeats it is two
**static** top-level imports that pull the heavy chunks into a scene's initial
graph rather than behind a dynamic boundary:

- **monaco** — `CSSCodeEditor.vue:14` `import * as monaco from "monaco-editor"` +
  `:26-27` `?worker` imports + `:29` `self.MonacoEnvironment`. The editor is
  *already* lazy at the panel level (`AnimationControls.vue:122-123`
  `defineAsyncComponent` for `KeyframesStringControls`/`KeyframeTimeline`), so
  monaco's 3.7 MB `vendor-monaco` chunk + the two workers correctly defer until a
  user opens the keyframes/timeline tab. **Verify** the built graph: assert that
  the app entry (`index-*.js`) does **not** statically reference `vendor-monaco`,
  and that the `editor.worker`/`css.worker` chunks load only on first editor
  mount. If any eager edge into monaco exists outside the async-component
  boundary, sever it (route the import through the `defineAsyncComponent`
  subtree). *Gestalt rationale:* a CSS editor is a power-user surface; it must not
  sit between the visitor and the home hero.

- **three** — `AmigaScene.vue:12-13` `import * as THREE from "three"` +
  `import { OrbitControls } from "three/examples/jsm/controls/OrbitControls.js"`.
  three (`vendor-three`) is *already* deferred at the scene level — `AmigaScene`
  is one of the `defineAsyncComponent` scenes (`scenes.ts`), so its chunk loads
  only when the visitor navigates to `/amiga`. **Verify** three is absent from the
  home/cube initial graph (the cube uses CSS-3D, not three — confirm no
  cross-scene three edge leaks into the eager set). The static imports inside
  `AmigaScene` are correct *because the scene itself is the dynamic boundary*; the
  failure mode to guard against is a shared util or barrel that re-exports three
  into a non-amiga eager path.

*Gestalt rationale:* "lazy-load monaco + three" is, on inspection, **mostly
already true** at the chunk level — the prod build never proved it only because
the build emitted no app graph at all. W4's lazy-load work is therefore (a) make
the build real (§1) so the split is observable, and (b) add a **regression
assertion** to the smoke gate (§Hard gate) that the entry chunk's static graph
excludes `vendor-monaco` and `vendor-three`. This converts an implicit
convention into a gated invariant — no future eager import can silently pull
3.7 MB onto the home critical path. No new chunking config, no workaround.

### 4 — Wire the chronic LoAF observer (dev-only, the consumer it always lacked)

The dev-only Long Animation Frames observer has been NAMED-FORWARD across two
tranches — raised in the grand-audit (`A/audit/constellation-grand-audit-2026-06-02.md`
§2.4), deferred in `A/waves/W4.md:144-148` and `A/FINAL.md:205-208`, with `grep
long-animation-frame|PerformanceObserver src/ demo/` → **0 hits** (re-confirmed
this audit). It was deferred each time for one reason: **no consumer** (the
overfitting precept requires ≥2 consumers or a demo). B.W4 is that consumer.

- **Add `demo/app/loaf-observer.ts`** — a dev-only, feature-detected
  `PerformanceObserver({ type: "long-animation-frame", buffered: true })` that
  records LoAF entries (duration, blocking-duration, attributed script source) and
  exposes them to (a) the prod-perf measurement (§5) and (b) the demo bench
  (`bench/playwright.bench.ts`). Gate on `import.meta.env.DEV` (a code condition
  bundlers DCE) **and** runtime feature-detection (`"PerformanceObserver" in
  window && PerformanceObserver.supportedEntryTypes?.includes("long-animation-frame")`)
  so it is a hard no-op in production and on non-Chromium browsers. Mount it from
  `main.ts` under the same `import.meta.env.DEV` guard so it ships zero bytes to
  the gh-pages bundle.
  *Gestalt rationale:* this is the **causal** half of A's `scheduler.yield()`
  group-batching claim, which has been unit-verified only (`test/engine-modern-web.test.ts`)
  and trace-unverified for two tranches. The observer attributes a >50 ms long
  animation frame to the active group/animation, turning the B.W3/B.W7 Playwright
  `>50ms`-trace gate (the other chronic stub) from anecdote into measurement.
  The two chronics close as **one** perf-evidence subsystem — observer + trace +
  assertion — exactly the gestalt the user mandated, not two more isolated
  deferrals (plan-findings.txt §"LoAF observer is chronic", design-findings
  perf items).

### 5 — Measure REAL prod-perf on the fixed build

The dev-mode lighthouse numbers on disk (`audit/lighthouse/_summary.json`) are
**not authoritative**: FCP 4.1-23.9 s, LCP 7.7-45.8 s, TTI 7.8-45.9 s. These were
captured against the dev server (un-minified, un-split, HMR runtime) *and* the
prod build was blank, so there was no real artefact to measure. They are a floor
of meaninglessness, not a baseline.

- **After §1-§3 land**, run lighthouse against the **built** `dist/gh-pages/`
  (served statically, mobile + desktop, all six routes), and record the result to
  `audit/lighthouse/after-prod/` as the *first authoritative* perf measurement
  keyframes.js has ever taken of its own demo.
- The improvement is reported **vs the currently-unmeasurable baseline** — i.e.
  the DELTA is "from a build that painted nothing (perf undefined) to a build that
  paints instantly with critical CSS + deferred heavy chunks." The hard gate (§)
  asserts the prod FCP/LCP are real, sub-threshold, and bounded — not a comparison
  against the dev-mode fiction.
- The LoAF observer (§4) annotates the run: any >50 ms frame in the measured load
  is attributed, so a perf regression names its cause rather than degrading the
  score silently.

*Gestalt rationale:* you cannot improve what you cannot measure. The first three
sections make perf *measurable*; this section makes the measurement *authoritative*
and hands B.W7 a real baseline for its full-π perf re-measure.

## § Hard gate (inv γ)

**The CI demo-build smoke gate asserts the gh-pages build emits a real entry that
mounts and paints.** A blank / tree-shaken build fails CI. This is **inv γ — the
demo cannot ship blank** (B.md §Inherited invariants). W4 *defines and proves* the
gate against the fixed build; B.W6 *wires it into `ci.yml`* as a standing job
(the two are paired — W4 makes the build pass it, W6 makes every future build face
it).

**Close conditions, each with its evidence:**

1. **Real entry, not a shim.** The built `dist/gh-pages/assets/index-*.js` entry
   chunk is non-trivial (orders of magnitude over the 698-byte polyfill — a
   concrete floor, e.g. `> 50 KB`, asserted) and statically references the Vue
   runtime + `App`. *Evidence:* byte-size assertion + a grep/AST check that the
   entry imports the app, not just the preload IIFE.
2. **CSS emits.** `dist/gh-pages/assets/index-*.css` exists and is non-empty.
   *Evidence:* file-presence + size assertion (today: zero `.css` assets — the
   binary failure this gate exists to catch).
3. **The app mounts and paints.** A headless run (Playwright, served from the
   built `dist/gh-pages/`) loads `/`, waits for `#app` to have child nodes that
   are **not** the loading skeleton, and asserts the home hero text is present and
   visible. *Evidence:* DOM assertion that `#app` is non-empty and the hero
   renders — a blank mount (the current state) fails.
4. **Heavy chunks are off the critical path.** The entry chunk's static import
   graph excludes `vendor-monaco` and `vendor-three`; the network trace for `/`
   shows neither monaco nor three nor the workers loaded at first paint.
   *Evidence:* Playwright network-request assertion (no `vendor-monaco`/
   `vendor-three`/`*.worker` request before `load`) + the modulepreload-exclusion
   already in `vite.config.ts:242-249`.
5. **No splash in the built output.** The built `index.html` `<body>` contains no
   `.loading-skeleton` / `.loading-title` / `keyframes.js` splash string and no
   hardcoded off-token hex. *Evidence:* string-absence assertion against the built
   HTML.
6. **Measured prod-perf is real and improved.** Lighthouse against the built
   `dist/gh-pages/` records authoritative FCP/LCP/TTI well under the dev-mode
   fiction (FCP and LCP each bounded by an explicit ceiling on both mobile +
   desktop; the critical-CSS path yields a fast FCP). *Evidence:*
   `audit/lighthouse/after-prod/` reports + a DELTA line stating "baseline =
   unmeasurable (blank build); after = paints in production with the recorded
   numbers." (The full-π perf re-measure is B.W7; W4 establishes the first
   authoritative point.)

The gate is green when a fresh `npm run gh-pages` produces a build that passes 1-6.

## § Design decisions (resolved choices, trade-offs)

1. **Extract to `main.ts`, not "mark the inline script as an entry."**
   *Resolved:* a real first-party module file referenced by `<script src>` is the
   idiomatic Vite/rolldown HTML entry — it is a graph root by construction, not by
   a fragile `treeshake`/`moduleSideEffects` override that would be a workaround
   masking the real shape. No `/* @vite-ignore */`, no `manualChunks` hack, no
   `injectScript` plugin. *Trade-off:* the bootstrap moves out of `index.html`
   into a sibling file — accepted; it is where every other Vite app keeps its
   entry, and it is the only place the CSS-cascade imports can be deterministically
   retained.

2. **The CSS cascade is imported from `main.ts`, explicitly.** *Resolved:* relying
   on SFC `<style>` blocks alone left the prod build with no top-level CSS entry
   the bundler would emit as a named `index-*.css` (the asset `criticalCSSPlugin`
   matches). Importing `@styles/style.css` + `@styles/utils.css` from the entry
   makes the CSS asset deterministic and named — which is *why* the previously-dead
   critical-CSS apparatus lights up for free. No new plugin; the existing
   `criticalCSSPlugin`/`deferLazyCSSPlugin` were always correct, they just had no
   input.

3. **No placeholder replaces the splash.** *Resolved:* instant-paint critical CSS
   (themed background + body geometry, zero JS, zero font) is the first paint; the
   hero is the app's true first frame mounted onto it. A retained placeholder is
   the exact content-swap flash the design audit flags. *Trade-off:* between
   `<style data-critical>` paint and the hero mount there is a brief blank-but-themed
   ground — accepted, and superior to a wrong-content splash; CLS stays ~0.006-0.01
   (measured) because the critical CSS reserves the layout.

4. **Lazy-load is mostly already true; W4's job is to *prove and gate* it.**
   *Resolved:* monaco (`AnimationControls.vue:122-123` async panel) and three
   (`scenes.ts` async scene) are already behind dynamic boundaries; the prod build
   simply never demonstrated it because it emitted no graph. W4 does not re-chunk —
   it makes the build real, then adds a smoke-gate assertion (Hard-gate condition
   4) that the home entry's static graph excludes `vendor-monaco`/`vendor-three`.
   This turns an implicit convention into a gated invariant. *Trade-off:* if a
   verification finds a genuine eager leak (a shared barrel re-exporting three into
   a non-amiga path), W4 severs it by routing the import through the existing
   async boundary — never by adding a new carve-out.

5. **The LoAF observer ships dev-only and clears overfitting by pairing.**
   *Resolved:* gated on `import.meta.env.DEV` + runtime feature-detect (Chromium
   only); zero bytes in the gh-pages bundle. It clears the overfitting precept
   because it now has two consumers — the prod-perf measurement (§5) and the demo
   bench (`bench/playwright.bench.ts`) — which is precisely the condition that kept
   it named-forward for two tranches. *Trade-off:* Chromium-only attribution —
   accepted; long-animation-frame is a Chromium-only API and the observer is a
   developer instrument, not a shipped engine feature. No engine-API surface
   changes (the opt-in engine hook the grand-audit floated stays unbuilt — no
   consumer; B.W2 owns the engine, and W4 keeps the observer purely demo-side).

6. **Dev-mode lighthouse numbers are explicitly disowned as a baseline.**
   *Resolved:* `audit/lighthouse/_summary.json` (FCP 4.1-23.9 s, LCP 7.7-45.8 s) is
   recorded as evidence the prod build was unmeasurable, **not** as a number to
   beat. The authoritative measurement is taken against the built `dist/gh-pages/`
   after §1-§3 (§5). *Trade-off:* there is no apples-to-apples "before" perf score —
   accepted, and correct: the honest DELTA is "blank → painting," and B.W7 carries
   the first real cross-build perf comparison once W4's authoritative point exists.
