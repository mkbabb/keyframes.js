The before/after edict (precepts SPEC.md "Before/after capture—every page,
paired, scripted") binds the capture to **a single Playwright/Chrome-MCP harness

  `_capture-report.json`); W7 points it at the W1-W6 integration HEAD and writes
  to `docs/tranches/B/audit/screenshots/after/<page>-<viewport>.png`—the path
  the edict mandates (`audit/screenshots/{before,after}/<page>-<viewport>.png`).
  WHY: identical harness + identical page×viewport matrix (6 pages × {mobile 375,
  laptop 1280, desktop 1440} = 18 captures, mirroring the 18 BEFORE) is what makes
  the pairing a true diff rather than two independent shoots.

  BEFORE was captured on the dev server (the prod build was blank—`index.html`
  bootstrap tree-shaken, B.md §Thesis 1). AFTER captures the W4-repaired build so
  the pairing reflects what ships. WHY: a dev-vs-prod pairing would diff two
  different artefacts; the edict's "pages not meant to change must be pixel-stable"
  only means something against the real shipped surface. This is the new
  before/after edict at full visual binding—NOT the build-floor.
- **The harness emits the AFTER `_capture-report.json`** (per-page status +
  `consoleErrors: []`) in the BEFORE format, so AFTER also discharges the demo
  smoke gate's runtime assertion (zero console errors on every page) at close.

## § Design decisions

1. **The SAME harness, re-run—not a second capture script (LOCKED).** The edict
   binds the before/after capture to "a single Playwright/Chrome-MCP harness
   checked into the tranche's audit dir so it re-runs identically at open and
   close" (precepts SPEC.md). W7 re-runs the W0 harness; authoring a second
   AFTER-only script would break the identical-harness contract and make the
   pairing a diff of two instruments, not one surface across time.

2. **AFTER captures the REPAIRED PROD build; BEFORE was dev (RESOLVED).** BEFORE
   was taken on the dev server because the prod build was blank (B.md §Thesis 1).
   AFTER captures the W4-repaired prod build—the surface that actually ships. The
   pairing is honest precisely because the AFTER side is the shipped artefact; the
   DELTA names this asymmetry explicitly so a future reader does not read the
   pairing as dev-vs-dev. This is the new before/after edict at FULL visual
   binding—the build-floor is NOT invoked, because B installed the tooling that
   makes full binding possible (the locked tooling-install decision).

3. **π binds at FULL—B discharges A's provisional π (RESOLVED).** A ran π at the
   build-verification floor on tooling-unavailability and recorded the verdict
   provisional, inheriting the re-probe as a named obligation (precepts SPEC.md
   Tooling-contingency clause; FINAL.md:131; plan-findings medium). B is the
   receiving tranche; the W7 close runs the full lane and records π as binding
   (not provisional)—the wave-spec does NOT carry a tooling-contingency floor
   note, because the contingency does not apply.

4. **The occlusion gate re-asserts on POPULATED scenes (RESOLVED).** BEFORE's
   amiga/square/easing/spring read "clean" in the occlusion report only because
   they were EMPTY (PROGRESS.md). The W7 occlusion cross-check runs against the
   W3-populated scenes—a meaningful gate must see a rendered subject. The DELTA
   explicitly states the BEFORE "clean" was vacuous so the AFTER green is not
   mistaken for "no change."

5. **The changeset bump tier turns on W2's `strict`-default, not on W1's majors
   (RESOLVED).** The library's own deps are already latest and W1's majors (zod
   3→4, vue-sonner 1→2, @iconify/vue 4→5, jsdom 26→29, vite-plugin-dts 4→5,
   @types/node 24→25) are demo/tooling-only (dep-upgrade-matrix)—none reaches
   the published `dist/`. So the published surface's breaking-vs-additive question
   is decided solely by whether W2's `parseOption` throws by default
   (major—breaking vs A's silent-default) or behind opt-in `strict`
   (minor—additive). The default is set in W2; W7 records the resulting tier.
   The version owner is named here so the publish leg is not orphaned
   (plan-findings info).

6. **The publish leg is user-domain, confirm-first—IDENTICAL to A (LOCKED).**
   W7 authors the changeset and stages the leg (version → tag → `release.yml`
   publish with provenance, the SAME path A established—FINAL.md §6, never
   rebuilt); the outward push runs only on explicit user authorization
   (PROGRESS.md §Cross-repo / outward perimeter item 3). The provenance leg
   (`id-token: write` + `--provenance`) is the standing publish path A made
   canonical; B reuses it unchanged.

7. **FINAL records, does not re-litigate, A's closed items (RESOLVED).** The three
   reconciled A defects (stale W4.md prose, lockfile prose, off-by-one) are
   corrected in B's FINAL as inherited-ledger fixes; the two cosmetic drifts
