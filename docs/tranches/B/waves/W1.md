# B.W1 — Dependency upgrade (matrix → gated bump)

> **Phase: IMPL (authored-now-run-later).** This wave is a binding plan, not an
> executed bump. No `package.json`/`package-lock.json` edit lands in development;
> the implementation phase opens only on explicit user authorization. The matrix
> below (`audit/dep-upgrade-matrix.txt`) is the ground truth this wave executes
> against when authorized.

## § Goal

**What lands:** keyframes.js' dependency graph at current-latest, behind a
single regression gate — every minor rolled in one pass, every major rolled with
a written breaking-change read and a per-major verification before it commits.

**Why:** A's scope was library-first; its dep posture was never measured. The W0
matrix proves the right thing about that posture and a wrong thing about its
risk distribution: **the two library deps are already latest** — `@mkbabb/value.js`
`^0.10.0 → 0.10.0` and `@mkbabb/parse-that` `^0.8.2 → 0.8.2` (matrix lines 4-5).
The publishable surface (`src/` → `dist/keyframes.{js,cjs,d.ts}`) has nothing to
bump. Every line of work in this wave is **demo + tooling** — the Vue/Vite/Vitest
toolchain, the shadcn-vue-scaffold deps the demo carries, and the dts roll-up
that builds the library's type artefact. This re-frames the wave from "risk to
the shipped library" (near-zero — externals are pinned and already-latest) to
"risk to the demo build and the type-emit pipeline" (the real surface), which is
exactly where the gate must bite. The gate is the regression bar A established
(`check:lib`/`build:lib`/`test`/`proof:boundary`) extended with B's new demo
smoke gate (inv γ, lands B.W6) so a dep bump cannot reintroduce the blank-prod
build the demo audit found.

### Majors — each individually, each with a breaking read

Six majors. Each lands as its own commit with its own gate run so a regression is
attributable to one dep, not a batch. The reads below are the binding pre-work.

#### zod `^3.23.8 → 4.4.3` — the headline risk

WHAT: bump zod across the v3→v4 boundary. WHY it is the headline: zod 4 is a
ground-up rewrite (new internal `ZodType` representation, changed error-issue
shape, `z.string().email()` → `z.email()` top-level relocations, stricter
`.default()`/coercion semantics).

THE READ — keyframes' zod surface is **transitive, not direct**. `npm ls zod`
resolves three nodes:
- `zod@3.25.76` (deduped) under `@vee-validate/zod@4.15.1`
- `zod@3.22.4` pinned under `prettier-plugin-classnames@0.10.2`
- `zod@3.25.76` direct (`package.json:107`)

A repo-wide grep for `from "zod"` / `toTypedSchema` / `useForm` / `vee-validate`
across `demo/` and `src/` (excluding `dist/`) returns **zero application call
sites** — there is no hand-written zod schema or vee-validate form in the demo;
zod is present as the `@vee-validate/zod` peer and the prettier-plugin pin. So the
real gate is the **`@vee-validate/zod` ↔ zod peer compatibility matrix**:
`@vee-validate/zod@4.15.1` (matrix line 11, itself already-latest) must declare
zod-4 in its `peerDependencies` range before the app's direct zod can move to 4.x
without a peer conflict. The read resolves to one of:
- **(a)** if `@vee-validate/zod@4.15.1` already accepts `zod@^4`, bump the direct
  `zod` to `4.4.3`, let `@vee-validate/zod` dedupe onto it, leave
  `prettier-plugin-classnames`'s pinned `zod@3.22.4` as an isolated tooling
  subtree (it never touches runtime).
- **(b)** if it does **not**, the app's direct zod stays at latest-3 (`3.25.76`)
  until `@vee-validate/zod` ships a zod-4 peer — record this as a held bump with
  the upstream PR/release as the trigger, do **not** force-resolve a peer conflict
  (that is the workaround the mandate forbids).

EVIDENCE the read produces: the resolved `npm ls zod` tree post-decision, plus a
`npm run dev` + `npm run gh-pages` build proving no form/validation path throws.
Because there are zero app schemas, the runtime blast radius is small; the risk is
purely the peer graph, which the read makes explicit.

#### vue-sonner `^1.1.3 → 2.0.9`

WHAT: bump the toast library across v1→v2. WHY a read: v2 is a Vue-3.5-era rewrite
(`<Toaster>` prop renames, `toast()` API surface changes). Resolved tree:
`vue-sonner@1.3.2` (`npm ls vue-sonner`). The demo **does** consume it — used in
`EasingSidebar.vue`, `CSSPasteDialog.vue`, `clipboard.ts`, the keyframes-editor
control cluster, `useShareState.ts` (grep hits, `vue-sonner` imports). THE READ:
enumerate every `toast.*(...)` call site and the single `<Toaster>` mount, diff
them against the v2 API (the `richColors`/`closeButton`/`position` prop names and
the `toast.success/error/promise` signatures), and list the rename set. This is a
mechanical rename surface, not a logic change — the read produces the exact
call-site diff so the bump is a find-replace verified by the build, not a guess.

#### @iconify/vue `^4.1.2 → 5.0.1`

WHAT: bump the icon component across v4→v5. WHY a read: v5 drops the legacy
`@iconify/vue` API arms and tightens the `<Icon>` component typing. Resolved tree:
`@iconify/vue@4.3.0` (`npm ls @iconify/vue`). THE READ: a repo grep for
`@iconify/vue` / `<Icon` returns **zero application call sites** in `demo/`+`src/`
(the demo uses `@lucide/vue` + `@iconify-json/radix-icons` data, not the
`@iconify/vue` runtime component directly). So the bump is low-risk; the read's
job is to confirm `@iconify-json/radix-icons@1.2.6` (matrix line 1, already-latest)
still resolves its icon data through `@iconify/vue@5` (the data-package ↔ component
contract), and that no shadcn-vue primitive imports the v4 component implicitly.

#### jsdom `^26.1.0 → 29.1.1` — the test env

WHAT: bump the test DOM across **three majors** (26→27→28→29). WHY a read: jsdom
is the `vitest` environment (`test/` runs under jsdom per `CLAUDE.md`); a major
jump can change `getComputedStyle`/`matchMedia`/`HTMLCanvasElement` stubs the
engine's DOM-aware paths lean on. THE READ — the at-risk tests are the ones that
touch DOM resolution: `units.test.ts` (computed unit / color parsing via
`getComputedStyle`), `morph.test.ts` (element-rect interpolation), `animation.test.ts`
(frame creation against DOM targets), and any `prefers-reduced-motion` `matchMedia`
stub. Enumerate the jsdom-version-sensitive assertions, run the suite under
`jsdom@29`, and confirm the computed-value pipeline (the `getComputedStyle` →
matrix-parse → sub-value extract flow noted in MEMORY.md) still resolves. EVIDENCE:
full green `npm test -- --run` under the new env; any jsdom-behavior delta
documented (jsdom 27+ tightened several CSSOM stubs — surface them, don't paper
over them).

#### vite-plugin-dts `^4.5.4 → 5.0.2` — the dts roll-up (careful)

WHAT: bump the type-emit plugin across v4→v5. WHY this one is delicate: A's
`vite.config.ts:206-216` carries a **deliberate custom pin** —
`entryRoot: "src/animation"` plus `compilerOptions.rootDir` pinned to the same
absolute path — because vite-plugin-dts 4 derives its rollup-stub path from
`relative(entryRoot, entry)`, which only matches the emit location when TSC's
effective `rootDir` equals `entryRoot`. The config comment
(`vite.config.ts:192-205`) documents the failure mode A hit: without both pins,
`src/animation/index.ts` emits to `dist/src/animation/index.d.ts` while the
stub-writer looks for `dist/index.d.ts`, and API Extractor rolls up an empty stub
yielding a **12-byte `export {}`** artefact — a silently-broken `.d.ts`.

THE READ: vite-plugin-dts 5 may change `rollupTypes` internals, the `entryRoot`
default resolution, or the underlying API Extractor version. The mandatory
verification is **not** "the build passes" — it is **`dist/keyframes.d.ts` is a
real, non-trivial declaration file**. The read must:
1. Confirm whether v5 still honors the `entryRoot` + `rootDir` lockstep, or
   whether v5 resolves the rootDir automatically (in which case the explicit pin
   may become redundant — but is removed only if v5 provably does the right thing,
   never speculatively).
2. After the bump, **byte-check** `dist/keyframes.d.ts`: assert it is >> 12 bytes
   and that `grep -c "export" dist/keyframes.d.ts` finds the real public surface
   (`Animation`, `CSSKeyframesAnimation`, `AnimationGroup`, `NumericAnimation`,
   `SmoothProgress`, `ElementMorph`, `Timeline`, `ScrollTimeline`,
   `ManualTimeline`, `RAFPlayback`, `getAnimationId`).
3. If v5 breaks the stub-path contract differently, the fix is the *correct* pin
   for v5's resolution model — no alias, no shim, no reverting to v4.

This is the single tooling bump where "green CI" is insufficient evidence; the
emitted artefact must be inspected. The dts roll-up *is* the library's type
contract.

#### @types/node `^24.12.4 → 25.9.1`

WHAT: bump the Node typings across v24→v25. WHY a read: B's `engines.node`
(`package.json:50-52`) is `>=22`; `@types/node@25` tracks the Node 25 API surface.
THE READ: confirm no build-script or `vite.config.ts` Node-API usage
(`path`, `import.meta.dirname`) breaks under the v25 typings, and that `check:lib`
(`tsc --noEmit -p tsconfig.lib.json`) stays green — `@types/node` is a `devDep`,

the `tsc` surface is clean.

### The v-calendar 'latest'-tag quirk — do NOT downgrade

The matrix (line 33) shows `v-calendar: ^3.1.2 → 2.4.2` flagged MAJOR — but
**2.4.2 is below the installed 3.1.2**. This is a registry **dist-tag quirk**:
v-calendar's `latest` npm tag points at the stable `2.x` line while the `3.x`
release sits behind a `next` (or pre-release) tag, so a naive "→ latest" resolver
reads it as a downgrade-major. **Disposition: hold at `^3.1.2` — do not downgrade.**
The read records this explicitly so a future "update to latest" pass does not
mechanically regress v-calendar to 2.x. (The demo's actual v-calendar usage is
nil per the grep — it is a shadcn-vue-scaffold dep — which makes the no-op safe;
the danger is purely an automated bump misreading the tag.)

## § Hard gate

WHAT closes the wave + the evidence that verifies it:

1. **Library gate green** — the A-established chain passes on the post-bump tree:
   `npm run check:lib` (tsc, src-only) · `npm run build:lib` (library entry) ·
   `npm test -- --run` (full vitest suite under the bumped `jsdom`+`vitest`) ·
   `npm run proof:boundary` (the value.js boundary gate). Evidence: the four
   commands exit 0; the suite count is unchanged or grows (never shrinks).
2. **dts artefact verified** — `dist/keyframes.d.ts` is byte-checked >> 12 bytes
   and `grep` confirms the eleven public exports are present (the vite-plugin-dts
   5 read's acceptance criterion). Evidence: the file size + grep output recorded.
   This gate exists specifically because "build passed" did not catch A's 12-byte
   `export {}` regression.
3. **Demo build paints** — `npm run gh-pages` emits a non-trivial entry, and the
   **new demo smoke gate (inv γ, lands B.W6)** asserts the gh-pages build mounts
   and paints. A dep bump that re-tree-shakes the bootstrap (the exact class of
   defect the demo audit found) fails here. Evidence: smoke gate green on the
   post-bump `dist/gh-pages/` output.
4. **Each major individually attributable** — every major lands as its own commit
   with its own gate run, so a red gate names the offending dep. Evidence: the
   commit-per-major history; no batched-major commit.
5. **Each major carries a written breaking read** — the six reads above are
   recorded with their resolved decision (bump / hold-with-trigger), not left
   implicit. Evidence: this spec's reads, updated at execution time with the
   actual resolved `npm ls` trees.

The gate's standard is A's "the gate must bite" bar (plan-finding info-level,
`scripts/proof-boundary.mjs` precedent): a regression must turn a gate red, not
slip through green. The dts byte-check and the demo smoke gate are the two
additions that close the holes "green build" alone left open.

## § Design decisions

Resolved choices and their trade-offs:

1. **Plan-as-wave, not executed-now (locked, inherited from B.md).** W1 is
   authored complete; the bump runs only on explicit authorization. TRADE-OFF: the
   matrix is a W0-snapshot; latest versions may drift by execution time. MITIGATION:
   the wave re-reads `npm outdated` at execution and reconciles any post-snapshot
   drift before committing — the matrix is the *method*, the live registry is the
   *truth* at run time.

2. **Library deps are the headline non-event.** The most important finding is that
   the publishable graph needs nothing — `value.js` and `parse-that` are latest.
   TRADE-OFF: a reader expecting "upgrade everything" may under-weight that the
   real surface is demo+tooling. The spec front-loads this so the gate is aimed
   correctly (at the demo build + dts emit), not at a library that has no bump.

3. **Majors land individually; minors batch.** RESOLVED: one commit per major
   (attributability), one commit for all minors (efficiency). TRADE-OFF: more
   commits vs. a single sweep. The attributability of a per-major commit is worth
   the extra commits — a red gate must name one dep, which a batched-major commit
   cannot do.

4. **zod 3→4 is gated on the peer graph, not app code.** RESOLVED: because the
   demo has zero zod/vee-validate call sites, the bump's only real constraint is
   `@vee-validate/zod`'s zod peer range. If that peer does not yet accept zod-4,
   the direct zod **holds at latest-3 with the upstream peer-release as the
   trigger** — a held bump, never a forced `--legacy-peer-deps` resolution.
   TRADE-OFF: the app may sit one zod-major behind until the peer catches up; the
   alternative (forcing a peer conflict) is the workaround the mandate forbids.

5. **vite-plugin-dts 5 is verified by artefact, not by exit code.** RESOLVED: the
   custom `entryRoot`/`rootDir` pin is treated as load-bearing; the bump's
   acceptance is a byte-and-grep inspection of `dist/keyframes.d.ts`, because A
   already proved a green build can emit a 12-byte empty stub. If v5's resolution
   model makes the explicit pin redundant, the pin is removed only with proof
   v5 emits the full declaration without it — never speculatively, never aliased.

6. **v-calendar holds at 3.x against the 'latest'-tag downgrade.** RESOLVED: the
   matrix's `→ 2.4.2` is a dist-tag artefact (latest=2.x, 3.x behind next), not a
   real newer release; v-calendar stays `^3.1.2`. TRADE-OFF: a future automated
   "→ latest" pass could re-trip this; the decision is recorded in this spec
   precisely so it cannot.

7. **No `--force` / `--legacy-peer-deps` anywhere.** RESOLVED across all six
   majors: a peer conflict is a *held bump with a trigger*, not a coerced install.
   This is the no-workaround mandate applied to the dependency graph — the lockfile
   must reflect a genuinely-resolvable tree (which also keeps B.W6's
   lockfile/inv-β reconciliation honest).
